# 垃圾桶前垃圾分类正确性判定与 sort 切换 1920×1080

> 整理日期：2026年11月20日 17:28
> 项目：ROS仿真车 ｜ 类型：功能开发 ｜ 状态：部分解决 ｜ 主题：`感知与视觉` `硬件与调试` ｜ 标签：`ros` `yolo` `perception` `openvino` `真车`

## 背景 / 目标

实车 `aic26_ws_112` 在 rubbish bin 站点依次跑 `rubbish`（8 类桶，含开/关盖）和 `sort`
（24 类垃圾卡），两份结果彼此独立，没有"这张垃圾卡在哪个桶前、类别对不对"的判断。

本次两个需求：

1. 依据 `表格.docx` 的四类 24 项类别表，判断垃圾桶前的小垃圾卡是否属于对应垃圾桶；
   **只在终端输出**，不加语音播报；垃圾是摆在桶前的小卡片；不考虑桶盖开/关。归属规则由用户
   明确指定为**严格包裹**（垃圾框必须完整落在桶框内）。
2. `rubbish` 与 `sort` 检测时的摄像头画面都切换到 **1920×1080**（原本只有 rubbish 切 1080p，
   sort 固定在 1280×720）。

## 报错记录 / 关键发现

### 1. GUI 结果与 ROS 结果的 boxes 结构不同

`detect_gui.py` 保存的 JSON 是 `boxes: [{class, conf, box}, ...]`，ROS 检测器的
`/perception/result` 是 `boxes: {class: [[x,y,w,h], ...]}`。离线复算必须同时兼容两种形式，
否则前者会被当成"没有可比较的结果"。

### 2. 严格包裹在参考数据上的实际表现

用 23:07 sort + 23:08 rubbish 实测（框均为 1920×1080 绝对像素）：

| 垃圾卡 | 所在桶 | 结果 |
|---|---|---|
| cigarette_butt 烟头 | kitchen_close（绿） | **完整落在桶框内**，判为投放错误（烟头属其他垃圾） |
| fishbone 鱼骨 | recyclable_open（蓝） | 下沿超出桶框 1.1 px，按严格规则判"未归属" |
| waste_roll 废胶卷 | other_open（灰） | 下沿超出 0.4 px，"未归属" |
| used_tissue 用过纸巾 | harmful_close（红） | 下沿超出 3.9 px，"未归属" |

即：**严格包裹在真实画面里非常苛刻**，卡片下沿即使只超出亚像素级也会变成"未归属"。这是规则
本身的语义，未加容差；实车验收要以卡片确实落在桶框内的画面为准。

### 3. 相机 reload 的语义与跨进程竞态

`camera_node.py` 的 `/camera/reload`（Trigger）：

- **在设备重开之前就返回**，`True` 只表示参数被 spin 循环读取，不代表 1080p 已出图；
- 设备重开实际发生在 `spin()` 里，约 0.8s，最坏 ~1.6s；
- `/camera/{width,height,fps}` 是普通参数，rubbish 与 sort 是**两个进程**，reload 没有跨进程
  串行化，**最后写入者生效**；
- 驱动不支持请求尺寸时会静默回落到实际尺寸，且不更新参数。

因此 rubbish 发布结果后恢复 720p、sort 紧接着请求 1080p 时，可能交错。sort 侧的对策是：
检查 `/camera/width/height`，被覆盖后 0.8s 节流重发；2.5s 内拿不到 1080p 帧就回退实际尺寸并
`logerr`，不耗光 8s 的 `sort_detect_timeout`。

### 4. 仿真没有 `/camera/reload`

Gazebo 相机固定 1280×720、无 reload 服务。`_set_camera_resolution` 先 `wait_for_service`，
服务不存在就直接返回失败，**不写 `/camera/*` 参数**，避免仿真里把参数污染成 1080p；随后走
回退路径。

### 5. 远端测试时 PYTHONPATH 覆盖

`PYTHONPATH=src/... python3` 会覆盖 ROS setup 设置的 PYTHONPATH，导致 `import rospy` 失败。
正确写法是 `export PYTHONPATH="$PYTHONPATH:<脚本目录>"`，或直接在脚本目录运行。

## 修改方案

### 1. 类别表与坐标归一化

`mission_common.py` 新增 `SORT_CATEGORY`（24 类 → `recyclable/other/kitchen/harmful`）：

| 桶类别 | 垃圾类 |
|---|---|
| recyclable 可回收物（蓝） | plastic_bottle、newspaper、glass_bottle、can、old_clothes、carton |
| other 其他垃圾（灰） | cigarette_butt、used_tissue、broken_ceramic、shell、disposable_chopsticks、broken_glasses |
| kitchen 厨余垃圾（绿） | fruit_core、fishbone、vegetable_leaf、bread、tea_leaves、leftover_rice |
| harmful 有害垃圾（红） | button_battery、fluorescent_lamp、waste_roll、paint、medicine_tablet、mercury_thermometer |

两个检测器的结果都增加 `image_size: [w, h]`，判定前各自除以自己的尺寸归一化到 `[0,1]`，
这样 1080p 的桶框和 720p 的垃圾框也能比较。GUI JSON 没有 `image_size` 时从 `source`
（`/dev/video0 1920x1080`）解析兜底。

### 2. 严格包裹判定

`mission_common.assess_bin_placements(rubbish, sort)`：

- 桶类别 = 类名去掉 `_open/_close`；
- 垃圾卡框必须满足 `bin.x0 <= item.x0`、`bin.y0 <= item.y0`、`bin.x1 >= item.x1`、
  `bin.y1 >= item.y1`；多个桶都包住时取**面积最小**的桶；
- 一个桶都不包住 → `unplaced`；
- `correct = SORT_CATEGORY[item] == 桶类别`；
- 未知类名跳过并在结果里列 `unknown`。

终端格式（`format_bin_check_lines`，只 `rospy.loginfo`，不播报）：

```text
[bin-check] 垃圾桶前垃圾判定：共 4 件，正确 0，错误 1，未归属 3
[bin-check]   [错误] 烟头 → 厨余垃圾桶(绿)，应投其他垃圾桶(灰)
[bin-check]   [未归属] 鱼骨（应投厨余垃圾桶(绿)）
```

`mission_controller.run_task` 的 inspect 分支里，`targets` 同时包含 `rubbish` 和 `sort`
且结果齐全时打印上述行；缺结果时打印一行"缺少 rubbish 或 sort 结果，跳过"。

### 3. sort 的 1080p 相机窗口

`sort_detector.py` 增加 4 态状态机 `idle → waiting → locked`，失败进 `fallback`：

- 参数：`highres_width/height/fps = 1920/1080/10`，`highres_settle 0.3`，
  `highres_timeout 2.5`，`highres_retry 0.8`，`highres_stall_timeout 1.0`，
  `normal_width/height/fps = 1280/720/30`；
- 请求/等待放在 0.1s 定时器里，**不阻塞 `on_detect`**；`_set_camera_resolution` 先探测服务
  再写参数；
- `on_image` 在限速之前做尺寸门控：`waiting/locked` 状态下非 1920×1080 的帧直接丢弃，
  观察窗只在第一帧 1080p 上开始；
- 参数被覆盖 → 0.8s 后重发；2.5s 无 1080p → `fallback` + `logerr`，按实际尺寸继续；
- 结束 / stop / 被其他 target 抢占 / SIGINT-SIGTERM 都恢复 1280×720@30；
- `highres_enabled:=false` 可一键退回原来的 720p 行为。

`sort.launch` 同步增加对应 `<arg>/<param>`；`mission.launch` 的 sort include 不用改。

## 结果与结论

- 垃圾投放类别判定已接入 mission，终端输出 `[bin-check]`，不播报；
- rubbish 与 sort 现在都会请求 1920×1080@10，并能处理彼此恢复/请求的交叠；
- 严格包裹规则在真实画面上很苛刻，参考数据 4 张卡里 3 张因下沿超出 0.4~3.9 px 被判"未归属"；
  如现场希望容忍几个像素，需要另行加外扩容差；
- sort 模型此前在 720p 数据上验证，1080p 下目标尺度变化可能影响 `total`/`max_conf`，
  联调时需对比；回退开关 `highres_enabled:=false`；
- `kill -9` 无法执行恢复，相机参数会停在 1080p，手动恢复：

```bash
rosparam set /camera/width 1280
rosparam set /camera/height 720
rosparam set /camera/fps 30
rosservice call /camera/reload
```

- 因此状态标为**部分解决**：代码、离线与状态机验证完成，实车完整 bringup 验证待做。
