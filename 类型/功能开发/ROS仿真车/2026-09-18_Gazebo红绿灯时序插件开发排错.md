# Gazebo 红绿灯时序插件开发与排错

> 整理日期：2026年9月18日 22:26

## 环境信息
- 操作系统：Windows 11（宿主机）+ Docker 容器内 Ubuntu 20.04
- ROS：Noetic（rosversion 1.17.4）
- Gazebo：11.15.1（Gazebo Classic，gzserver + gzclient 分离架构）
- 构建：catkin_ws + catkin_make，功能包 `visual_plug`
- 目标：实现红绿灯按 红灯10s / 绿灯15s / 黄灯5s 循环亮起

## 报错记录（按排查顺序）

1. **`[Err] Publishing an uninitialized message ... Required field [parent_name] missing`**
   - 原因：`msgs::Visual` 的 `parent_name` 是 protobuf 必填字段，消息未设置时 publish 直接拒收。
2. **`[Err] Connection.hh:293 Header is empty` / `Master Unknown message type`**
   - 原因：gzserver 无界面运行时连不上 gzclient 的通信噪音，不影响插件。
3. **`[Err] InsertModelWidget.cc:403 Missing model.config for model "/root/.gazebo/models/.git"`**
   - 原因：把整个仓库（含 .git）平铺进了 ~/.gazebo/models/，Gazebo 把 .git 当模型目录扫描。无关噪音。
4. **灯不亮（最终根因）**：`traffic_light_green_lens/model.sdf` 大小是 **4189 字节**（门架主体的大小），而正确透镜 sdf 应为 **~719 字节**。即 `docker cp` 时误把门架主体的 `model.sdf` 覆盖进了三个 lens 目录，导致 lens 目录实际加载的是门架主体（link 叫 `gantry`，只有 `*_lens_off` 熄灭透镜），没有 `lens` link 和 `red/yellow/green_visual` 发光视觉，插件消息永远匹配不到目标。

## 修改方案（关键结论）

### 1. 插件架构（最终采用）
- **WorldPlugin**（挂在 `<world>` 下，不是 model 级），因要控制多组红绿灯。
- 用 **transport `~/visual` 消息**改颜色，**不能**用渲染 API（`rendering::get_scene()`）——因为 WorldPlugin/ModelPlugin 跑在 gzserver 进程，渲染在 gzclient 进程，直接调渲染 API 永远拿 null。
- 消息字段正确组合（经过多轮试错确认）：
  - `name` = `lens::red_visual`（link::visual 两段）
  - `parent_name` = `traffic_light_top_red_lens`（模型名）
  - 渲染端拼成 `模型名::link::visual` 三段查找
- 发光透镜控制：亮 = diffuse 亮色 + emissive 发光，灭 = diffuse 暗色 + emissive 黑。

### 2. 模型库结构（roscar-gazebo-models）
- 门架式红绿灯 = 1 主体 + 3 发光透镜独立 model：
  - `traffic_light`（主体，含 `*_lens_off` 熄灭透镜）
  - `traffic_light_red_lens`（link `lens`，visual `red_visual`，带 emissive）
  - `traffic_light_yellow_lens` / `traffic_light_green_lens`（同理）
- 横向排布：红左(x=-0.12)、黄中、绿右(x=+0.12)。

### 3. world 文件写法
- 每个红绿灯 = 1 主体 + 3 透镜，共 4 个 `<include>` 叠在同一 pose。
- `<name>` 重命名：主体 `traffic_light_top`，透镜 `traffic_light_top_red_lens` 等。
- WorldPlugin 用 `<group>` 前缀 `traffic_light_top` / `traffic_light_bottom` 关联。

### 4. CMakeLists.txt（catkin 版，5 处改动）
- `find_package(gazebo REQUIRED)`、`add_compile_options(-std=c++14)`、`include_directories(${GAZEBO_INCLUDE_DIRS})`、`link_directories(${GAZEBO_LIBRARY_DIRS})`、`add_library(traffic_light_plugin SHARED ...)` + `target_link_libraries(... ${GAZEBO_LIBRARIES})`。

### 5. 关键环境依赖
- `GAZEBO_PLUGIN_PATH` 需含 `/root/catkin_ws/devel/lib`（写进 ~/.bashrc，否则 roslaunch 找不到 .so）。
- 模型放 `~/.gazebo/models/`（每个模型目录直接含 model.config + model.sdf，不能嵌套）。

## 结果与结论
- 插件逻辑、消息格式、时序循环均已验证正确（gzserver 日志显示 `[TrafficLight] LOADED` + `-> GREEN/YELLOW/RED` 正常循环，`parent_name missing` 错误已消除）。
- 灯不亮的**最终根因已定位**：三个 lens 目录的 `model.sdf` 被门架主体误覆盖（4189 字节 vs 应为 719 字节）。
- **修复方案已给出但尚未确认生效**：用 heredoc 覆盖三个 lens 的 `model.sdf` 为正确的透镜内容（含 `lens` link + `*_visual` + emissive），然后重跑 gazebo。
