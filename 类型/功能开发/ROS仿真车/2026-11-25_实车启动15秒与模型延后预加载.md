# AIC26 实车启动 15 秒与检测器延后预加载

> 整理日期：2026年11月25日 07:22
> 项目：ROS仿真车 ｜ 类型：功能开发 ｜ 状态：进行中 ｜ 主题：`感知与视觉`、`导航与运动控制` ｜ 标签：`ros`、`perception`、`openvino`、`真车`、`move_base`

## 背景 / 目标

用户要求把 `aic26_ws_112` 实车 bringup 的预启动时间压缩到 **15 秒内**，并把非首批任务的检测模型预加载挪到“小车启动之后”。

任务流程最前面的检测点是：

- `leave_start`：纯导航；
- `light_1`：红绿灯，需要 `traffic_light`；
- `people_a1` / `people_a2`：人员 + 违停电动车，需要 `people` 和 `ebike_park`；
- 之后的 `sign_gate` 才第一次用到 `sign`；楼宇、火情、温度、louyud、仪表、车辆、垃圾、sort、ebike_pano 都在更后面。

因此首批只需要 `traffic_light`、`people`、`ebike_park` 三个模型；其余模型理论上可以在车开始行驶后再加载。

本轮只完成了代码与日志分析、方案设计和风险评估，**尚未改动实车代码或 launch**。

## 现状与耗时数据

### 01:37 正常热启动

以 roslaunch 启动为 0 点，日志中的关键时间：

| 事件 | 相对时间 |
|---|---|
| `mission_controller` init_node | 约 +10.2 s |
| `move_base action server is up` | 约 +11.7 s |
| `people detector protocol v2` | 约 +12.1 s |
| `traffic_light detector protocol v2` | 约 +13.0 s |
| `ebike_park detector protocol v2` | 约 +16.5 s |
| `louyud detector protocol v2` | 约 +17.9 s |
| `mission started, 14 tasks` | 约 +17.9 s |

结论：正常启动约 **17.5–19 秒**，不是 nav 或 early detector 拖慢，而是 **mission 在等最后一个 staggered 的 `louyud` protocol**。

### 04:27 冷启动异常

同一天 04:27 的一次 run 到 +38.1 s 才 `mission started`。日志显示：

- `global_costmap` 在请求地图后卡了 **30.01 s**（`Requesting the map...` 到 `Resizing costmap...`）；
- 同一时段 13 个 ONNX 模型在 4 核 CPU 上集中编译；
- 这是模型加载/nav 资源竞争导致的 outlier，不是每次启动都发生。

## 根因

### 1. 启动门禁按“全任务树”等待

`mission_controller.run()` 先递归收集整个任务树的所有检测目标，得到 13 个 target：

```text
traffic_light, people, ebike_park, sign, building, fire,
temperature, louyud, gauge, car, rubbish, sort, ebike_pano
```

然后 `wait_protocols(required)` 要求 **13 个 target 全部** 达到 schema v2 才继续。条件只在启动阶段检查一次；`start_detect()` / `wait_result()` 在任务点不再检查 protocol。

### 2. `task_delay` 同时控制 mission 和所有检测器

`bringup.launch` 里 `task_delay=8.0`：

- 所有基础检测器先 `sleep 8.0`；
- `mission_controller` 也用同一个 `task_delay` 作为 `node_delay`；
- `sort` 额外 +4 s、`fire` +2 s、`ebike_park` +6 s、`louyud` +8 s。

因此 `louyud` 的 protocol 最早也只能在 `8 + 8 + 模型加载` 之后出现，成为启动门禁的最后一块木板。

### 3. 模型在节点 `__init__` 中同步加载

检测器先 `YoloNet(...)` 加载模型，再发布 latched protocol。协议出现时间 = `node_delay` + rospy 初始化 + 模型编译/加载。没有“只启动进程、等第一次请求再加载模型”的现成机制。

## 推荐方案（尚未实施）

### A. 启动门禁只等首批 target

在 `mission_controller.py` 增加参数，例如：

```yaml
startup_targets: "traffic_light,people,ebike_park"
late_protocol_wait: 10.0
```

`run()` 里把 `required` 拆成：

- `early_required = required ∩ startup_targets`
- `deferred = required - early_required`

启动阶段只 `wait_protocols(early_required)`；日志列出 deferred targets，避免误以为所有模型都已就绪。

### B. 延后 target 在首次使用前再等 protocol

新增 `ensure_protocol(target)`，在 `start_detect()` 发布 `/perception/detect` 之前调用：

- 若该 target 已有 v2 protocol，直接通过；
- 否则最多等 `late_protocol_wait`（建议 10 s），超时后记录 warning 并照常发请求；
- 原有的 `wait_result()` 超时继续作为最终兜底。

这样即使某个延后模型还没启动/加载完，第一次用到它时会自动等待，而不是请求直接丢失。

### C. 用 launch 的 `node_delay` 重排模型加载

所有检测器仍是 roslaunch 启动，只是用 `sleep` 把进程启动时间推后；不需要新增 service 或动态 spawn：

- 新增 `mission_delay`（建议 0–1 s），让 `mission_controller` 不再跟 `task_delay` 绑定；
- `traffic_light`、`people` 在 2–3 s 启动；
- `ebike_park` 在 4–5 s 启动；
- `sign` 及之后的模型放到 20 s 以后，按 5–10 s 间隔错开，例如：

| 检测器 | 建议启动相对时间 |
|---|---:|
| sign | 20 s |
| building | 30 s |
| fire | 35 s |
| temperature | 40 s |
| louyud | 45 s |
| gauge | 50 s |
| car | 60 s |
| rubbish | 65 s |
| sort | 70 s |
| ebike / ebike_pano | 80 s |

数值只是建议值，需要根据实车路线时间与 CPU 负载再调。`nav_delay` 暂保持 5 s，因为 nav 栈本身仍需要启动时间。

### D. 预期时间线

若首批模型在 5–9 s 就绪，mission 在 `wait_ready()`（nav / TF / start align）完成后即可开始：

- `mission_controller` 初始化：约 +2 s；
- nav 可用：约 +12 s（受 nav_delay 影响）；
- 首批 protocol：约 +5–9 s；
- `mission started`：预计 **+12–14 s**，可进入 15 s 目标。

`wait_ready()` 中的 `start_align()` 本身可能先让车动一下；如果以“车第一次动”为计时终点，可能比 `mission started` 更早。

## 风险

1. **CPU 竞争**：把模型加载推到行驶阶段后，多个 44 MB fp32 模型仍可能在 4 核 N100 上同时编译，重现 04:27 的 move_base 地图请求卡 30 s。必须错峰启动并监控 `top` / rosout。
2. **延后模型未就绪**：`/perception/detect` 不是 latched；如果节点还没起来就发请求，请求会丢。`ensure_protocol()` 只能缓解，不能保证模型已加载完。
3. **协议心跳 ≠ 请求路径健康**：protocol 1 Hz 只说明 publisher 活着；detect 订阅、result 发布、相机图像仍可能断。不能把 protocol 当成完整通信健康检查。
4. **people / car 的 protocol 只发一次**：它们没有 1 Hz 重发；如果 mission 启动早于节点，必须靠 `wait_protocols` 或 `ensure_protocol` 等 latched 消息，不能靠周期心跳。
5. **相机重载**：`sort`、`rubbish`、`gauge`（以及 `highres:=true` 的 layout）在激活时会调用 `/camera/reload` 改写共享相机参数；延后启动不会改变这一点，但行驶中激活可能短暂影响其他消费者。
6. **失败路径变长**：如果首批检测器真的起不来，`protocol_wait=30` × `protocol_retries=2` 的最坏等待仍是 90 s；本轮不建议改这个兜底，只改“正常路径等谁”。
7. **未实测**：以上是日志分析 + 方案设计，15 s 目标尚未在实车验证；需要先跑一轮带时间戳的完整任务。

## 附：运行期自主通信检测的风险（仅分析）

当前任务运行时没有主动心跳/watchdog，只有每个请求的 `wait_result` 超时：

- 多数检测器 1 Hz 重发 protocol，但 `last_seen` 没有被记录；
- `people` / `car` 只发一次；
- 检测器 `respawn="true" respawn_delay="5.0"`；
- `hardware_status` 只监控 5 个传感器 topic，不监控检测器通信。

若只做轻量版“记录 last_seen + 告警”：

- **低风险**：日志噪声、少量 CPU；
- **中风险**：1 Hz 定时器被推理/GIL 拖慢导致误报；respawn/启动窗口误报；`last_seen` 线程竞争；
- **高风险**：把 protocol 心跳当成通信健康，出现“心跳正常但 detect/result 路径已断”的漏报；若用心跳自动跳过/重试，误报会直接造成漏检或拖慢任务。

结论：轻量版适合做“advisory 告警”，不适合作为自动跳过/重试/中止的依据；真正的请求路径健康检查需要额外的 ping/ack 或 master 订阅状态查询，已超出轻量范围。
