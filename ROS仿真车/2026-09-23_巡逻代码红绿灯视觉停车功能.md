## 报错记录 / 需求

- 需求二：接近指定点前，由**视觉模块判断红绿灯**——红灯停下、绿灯不停继续前进；视觉模块未完成，函数先**默认返回 True（视为红灯）**，并抽成独立函数便于日后替换。

## 修改方案
1. 新增独立函数 `check_traffic_light(px, py)`：
   - 返回 `True` = 检测到红灯（停车）；`False` = 绿灯（继续）。
   - 内部预留 YOLO 接口注释（`get_camera_image()` / `yolo_model()` / `contains_red_light()`），当前 `return True` 占位。
   - 未来接 YOLO 只改这一个函数内部，主循环不动。
2. 配置区新增红绿灯停车参数：
   - `STOP_POINTS = [(0.0, 1.60)]`（红绿灯位置，可多个）
   - `APPROACH_RADIUS = 0.8`（接近半径，进入才触发判断）
   - `STOP_DURATION = 5.0`（红灯停车时长）
   - `STOP_EVERY_LAP = True`（每圈经过都判断）
3. 状态变量：`stopping` / `stop_until` / `check_visited`（当前接近区内已判断的点）/ `checked_once`（只判断一次时用）。
4. 主循环插入两段：
   - **红绿灯判断段**：遍历 `STOP_POINTS`，进入 `APPROACH_RADIUS` 且未判断过 → 调 `check_traffic_light`，红灯则 `stopping=True` 并设 `stop_until`，绿灯则继续。
   - **停车状态机段**：`stopping` 且 `now < stop_until` 时持续 `pub.publish(Twist())`（零速）并 `continue`，到时后解除。
5. 定时用 `rospy.get_time()`（仿真时间），保证 Gazebo 里停 5 秒是仿真 5 秒。

## 结果与结论
- 功能骨架完成：当前默认「红灯」，小车接近 `(0.0, 1.60)` 半径 0.8 米内会停车 5 秒再继续；绿灯分支已预留，等 YOLO 接好后生效。
- 未实测运行，需在 Gazebo 中验证触发（观察 `rospy.loginfo("检测到红灯...")` 是否打印）。
- 注意点：`APPROACH_RADIUS` 须大于路径跟随精度，否则可能永远不触发；后续若要「红灯停、看到绿灯再走」，需把停车退出条件从「计时到」改为「再次调函数返回 False」。

1. 新增独立函数 `detect_traffic_light()`：返回 `'red' / 'yellow' / 'green'`，当前恒 `return 'red'`，内部留 TODO 注释（后续订阅 `/camera/image_raw` + cv_bridge + YOLO）。

   - `LIGHT_WAIT = 5.0`（红灯/黄灯停车等待秒数）
3. 状态变量：
   - `stop_start_time = None`（停车开始时刻，非 None 表示停车中）
   - `active_zone_idx = 0`（当前激活检测点索引）
4. 主循环红绿灯段（仅检测**当前激活点**）：
   - 进入触发区且未在停车 → 调 `detect_traffic_light()`
     - 红灯/黄灯 → 记录 `stop_start_time = now`，停车
     - 绿灯 → 直接放行并 `active_zone_idx = (idx+1) % len`，切到下一个点
   - `now - stop_start_time >= LIGHT_WAIT` → 放行并 `active_zone_idx` 切到下一个点
5. 停车时 `cmd.linear.x = cmd.angular.z = 0.0`，其余走原纯跟踪逻辑。
6. 计时用 `rospy.get_time()`。

### 结果与结论（补充）
- 逻辑已实现并通过 `python -c "import ast; ast.parse(...)"` 语法检查；**未在 Gazebo 实测**。
- 「每点消费一次」机制：检测点处理后立即切到下一个，避免车停在原区内反复触发/重置计时。
- 注意点：`LIGHT_RADIUS=0.2` 很小，20Hz 下 `MAX_V=0.4` 一帧约走 2cm，检测窗口约 0.5s；接入真实 YOLO 若单帧推理较慢，建议把半径调到 0.4~0.5。

## 补充：检测点读红绿灯 + 「一直 red」排查（2026-09-30 21:55）

### 需求
检测点从「无条件停 5 秒」改为**读 YOLO 红绿灯结果**：红灯/黄灯停车等待，绿灯马上继续前进。

### 修改方案
1. 新增 `detect_light()`：调 `/yolo/detect`，从返回 JSON 读 `red`/`yellow`/`green` 计数，返回灯色；优先级 red > yellow > green；未检出返回 `unknown`。
2. 检测点逻辑重写：
   - 进点停车 → 立即检测一次红绿灯。
   - **绿灯/unknown → 立即放行**（`detecting=False`），切下一个检测点。
   - **红/黄灯 → 停车**，每 `REDETECT_INTERVAL=1.0s` 重检一次，直到绿灯放行。
3. 参数：删除 `DETECT_WAIT=5.0`，新增 `REDETECT_INTERVAL=1.0`。
4. `detect_start_time` 语义从「停车开始时刻」改为「上次检测红绿灯时刻」。

已提交推送 `feature/nav-slam`（提交 `6e73f1c`「检测点改为读取红绿灯结果，红黄灯停车、绿灯继续」）。

### 报错：终端一直返回 red
**现象**：检测点反复输出 `{"traffic_lights": 1, "red": 1}`（每秒一次，持续 >1 分钟），小车一直停在检测点。

**排查过程**：
1. 排除代码问题：`detect_light()` 逻辑正确，stage2 类别映射正确（`{0:red, 1:green, 2:yellow}`）。
2. 排除模型对纯色误判：纯红/绿/黄色块喂 stage2 均无检测框（stage2 需真实红绿灯纹理）。
3. **实锤根因**：对照日志时间线 —— 红绿灯控制器在 13:32:33 把 1 号灯切为 **green**，但同一时刻 YOLO 仍返回 `{"red": 1}`。即 **stage2 模型把绿灯误判成红灯**。
4. 数据量佐证：stage2 训练数据仅 **24 张图**（red 6 + green 10 + yellow 8），严重欠拟合，极易学偏。
5. 模型一致性确认：容器内 `best.pt` / `tl_state_det.pt` 与桌面 `aic26小车视觉模块` 对应文件 **MD5 完全一致**，非拷贝损坏，是模型本身质量问题。

### 结果与结论
- 「检测到绿灯马上继续前进」的**代码逻辑已存在且正确**；未生效的根因是 stage2 模型 `tl_state_det.pt` 把绿灯误判成红灯，导致绿灯分支永远走不到。
- 待解决（按用户决定「不改，仅确认」暂不处理）：
  - 治本：补足绿灯样本重训 stage2。
  - 兜底：改读红绿灯控制器已发布的真实灯色话题 `/traffic_light/{id}/state`（latch=True），100% 准确但退化为读仿真内部状态。

### 修改方案

#### 1. 红绿灯检测点保存 yolopng（需求 I）

#### 2. 红绿灯两条路线（需求 J）

#### 3. 坐标重叠排查（需求 K）

#### 4. 任务点转 180° + 转 3 次（需求 L，核心 bug）
**现象**：任务点原地「转 90°」实际转 ~180°；同一点连续触发 3 次（日志 06:23~06:24 任务点2 连转 3 次）。

**根因（两个独立问题）**：
- **转 180°**：底盘是**四轮滑移转向**（`gazebo_ros_skid_steer_drive`），原地转时轮子打滑，odom 从轮速推算的 yaw **低估实际转角**。原代码用 `task_accum += normalize_angle(pyaw - last_yaw)` 累积 odom 增量判「转到 90°」→ odom 够 90° 时车体已转 ~160-180°。日志铁证：rotate_right 耗时 3.5s（理论 90°@0.8rad/s 仅 1.96s）。
- **转 3 次**：`task_armed`「离开圆即重新武装」无滞回，车转回后仍在圆附近 → 反复触发。

**修复**：
- 旋转改**开环定时**：直接发固定角速度持续 `角度/角速度` 秒（`TASK_ROTATE_DURATION = π/2 ÷ 0.8 = 1.96s`），不依赖打滑污染的 odom。旋转点同理（`SPIN_ROTATE_DURATION`）。
- 触发次数改**每圈重置**：`task_armed`/`spin_armed`/`zone_armed` 在「完成一圈切换路径」时统一 `[True]*len`，每点每圈只触发一次。
- 删除残留变量 `spin_accum`/`spin_last_yaw`/`task_accum`/`task_last_yaw`。

### 结果与结论
- `py_compile` 通过，无残留 odom 累积变量引用。
- 开环计时依赖 `TASK_W=0.8` 命令角速度被底盘准确执行；若实测 90° 有偏差（滑移底盘实际转速与命令值有增益差），微调 `TASK_ROTATE_DURATION` 补偿即可，不会再出现 180° 大偏差。
- 任务点3 与旋转点3 的重叠是**用户确认的故意复合动作**（先左转后右转），保留未改。
