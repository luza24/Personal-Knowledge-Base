# 真车迁移：导航改用 TEB 局部规划器 + 航点表重构

> 整理日期：2026年10月15日 19:37
> 项目：ROS仿真车 ｜ 状态：部分解决 ｜ 标签：`部署迁移` `ros` `move_base` `teb` `真车`

## 背景 / 目标

`oi~ -智慧社区复赛工程代码`（catkin `src/`）是 Gazebo 仿真工程，其**导航部分完全不走 move_base**：
`aic26_navigation/scripts/patrol_spin.py`（723 行）自己以 20Hz 直接发 `/cmd_vel`，用 `WaypointFollower`
做「到角点→原地转正→直行」的裸跟随 —— 没有避障、没有减速、没有局部规划。

这在仿真小场地（约 2.8m×3.4m、无障碍）够用，挪到真车（真实场地 21.12m×8.0m、有墙/家具/行人）就不合适。

**目标**：把任务层改成**航点表驱动的 move_base action 客户端**，由 **TEB 局部规划器**负责实际运动与避障，
任务行为（红绿灯、±90° 检测、车牌识别、掉头）在「停靠点」执行。

## 环境信息

- 编辑端：Windows 11（中文，默认 GBK 代码页）
- 仿真：Ubuntu 20.04 + ROS Noetic + Gazebo 11
- 真车：ROS Noetic；**麦克纳姆轮全向底盘**（`/cmd_vel` 支持 `linear.y`）；镭神 N10_P 雷达（`/scan`）；
  维特 WIT IMU（`/wit/imu`）；usb_cam（`/usb_cam/image_raw`）；EKF（robot_localization）融合 → `/odom` + TF
- 局部规划器：`teb_local_planner/TebLocalPlannerROS`（DWA 参数文件保留作回退）

## 关键前提（两条日志事实，已逐行核实）

1. **真车地图与仿真地图完全是两套坐标系**：真车 `resolution: 0.01`、`origin: [-7.0, -1.0, 0.0]`、
   2112×800px = **21.12m × 8.0m**（X∈[-7.0, 14.12]，Y∈[-1.0, 7.0]）；仓库里的
   `aic26_slam/maps/nav.yaml`（0.05、origin[-6,-6]）是**仿真**地图。→ **仿真坐标一个都不能复用**。
2. **真车 `/odom` 的 yaw 可用**：真车 EKF 是 `odom0_config` 位置全 false（x/y 相对开机点）、
   `imu0_config` 姿态全 true（yaw 来自 IMU 绝对航向）。这正是仿真缺、只能靠 `/gazebo/model_states`
   地面真值补的那一环 —— 仿真里 `/odom` 不可用是因为滑移转向插件的里程计由**指令速度积分**得出、与物理脱节。

## 报错记录 / 实施中踩到的坑

**1. `open()` 未指定编码 —— 中文 Windows 读 UTF-8 YAML 直接崩**

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0x80 in position 85: illegal multibyte sequence
```
航点表 `patrol_route.yaml` 里有中文注释，而中文 Windows 上 `open(path,'r')` 默认走 GBK。
**最阴的地方**：真车是 Linux 默认 utf-8，所以在车上能跑通、反而是 Windows 上编辑的副本读不了。
→ 必须写死 `open(path, 'r', encoding='utf-8')`。
（同一类坑还有 Windows 检出文件的 CRLF 让 shebang 变成 `python3\r`。）

**2. XML 注释里写了 `--` —— `roslaunch` 拒绝解析**

`--noarr` 这类命令行参数直接写进 `<!-- -->` 里是非法的（XML 禁止注释内出现 `--`）。
本次在 3 个 launch 文件里都中招（`nav.launch` / `bringup_drive.launch` / `bringup_nav.launch`）。
→ launch 注释里不要出现连续两个短横，改用文字描述。

**3.** `patrol_mission.py` 漏 `import json`（`YoloClient` 用到）。

**4.** 一行写坏的 `if False else` 残留表达式。

> 前两个都是"在 Linux 上不会暴露、在 Windows 上必炸"的类型，靠静态校验才捞出来。

**5. 改完之后把仿真路径改坏了（自查发现，已修）**

用户问"改后的代码还能在原 ros_noetic_gazebo 容器里跑吗"，回查发现三处回归：

| 回归 | 位置 | 后果 | 修法 |
|---|---|---|---|
| 脚本改名后旧名残留 | `setup_env.sh:450` | 提示仍打印 `patrol_spin.py`，仿真启动报找不到 | 改成 `patrol_spin_sim.py` |
| 默认地图指向不存在的文件 | `nav.launch` 的 `map` 默认 | 裸跑 `nav.launch` 起不来 | 见下 |
| `sensor_frame` 写死 `laser_link` | `costmap_common_params.yaml` | 仿真 TF 树里没有 `laser_link`（**仿真 frame 是 `laser`**，见 `gazebo_laser.xacro:107`），costmap 拿不到激光 → move_base 无输入 | 加 `laser_frame` arg |

**教训**：`<rosparam file=...>` **不做 `$(arg)` 替换**，所以想切换 YAML 里的值只能用
`<param name="ns/key" value="$(arg)"/>` 覆盖，且**必须放在 `rosparam load` 之后**
（后设置的叶节点才会盖住 YAML 载入的整块 `scan` 字典）：

```xml
<arg name="laser_frame" default="laser_link" />
...
<rosparam file=".../costmap_common_params.yaml" command="load" ns="global_costmap" />
<param name="global_costmap/scan/sensor_frame" value="$(arg laser_frame)" />
```

结论：`nav.launch` 的默认值保持**真车**（真车是主交付目标，且地图缺失时会**大声失败**
而不是静默用错地图），仿真必须显式传三个参：

```bash
roslaunch aic26_navigation nav.launch use_sim_time:=true laser_frame:=laser rviz:=true \
    map:=$(rospack find aic26_slam)/maps/nav.yaml
```

真正的仿真演示路径（Gazebo + perception + `patrol_spin_sim.py`）**不受影响** ——
`patrol_spin_sim.py` 自己发 `/cmd_vel`，根本不用 move_base，所以不需要起 `nav.launch`。

## 修改方案

### 1. 架构：一张有序航点表取代"半径触发 + 优先级阶梯"

仿真现状是「1 条开放路径 + 4 张半径触发点表」，每帧按优先级阶梯
（掉头 > spin > task > 车牌 > 红绿灯 > 跟随）裁决。改成**一张有序停靠点表**：

```yaml
stops:
  - {name: gate_1,   x: 0.90, y: 1.70, action: gate}
  - {name: spin_1,   x: -1.00, y: 1.90, action: spin}
  - {name: task_b2,  x: -0.30, y: -0.10, action: task, bucket: B}
  - {name: plate_1,  x: 0.80, y: -1.70, action: plate, plate_radius: 0.2}
  - {name: finish,   x: 1.75, y: 1.75, yaw_deg: 180.0, action: park}
```

- `action` ∈ `{none, gate, spin, task, plate, park}`；`stop: false` 的点只作路径塑形、不停车
- **`yaw_deg: null` = 自动取"朝向下一个停靠点"的方位角** —— 现场标定只需点 x/y，朝自由路径几何导出
- 航点表放 YAML 而非 Python：本次迁移**主要成本就是现场重新标定**，改 YAML 重启即可，且避开 Windows 编辑 .py 的 CRLF 风险

三处**行为变更**（不是等价重构）：半径触发变成显式停靠（车会停下再转、检测、转回）；
`CHECKPOINT`/`DEPART_DIST`/`RETURN_DIST`/`armed[]` 全部删除（有序表没有"终点离起点 0.07m"的歧义）。

### 2. `/cmd_vel` 的单写者约束（首要架构约束）

**任意时刻 `/cmd_vel` 只能有一个发布者** —— 真车 `newt.py` 直接把它转发到串口，两个来源会互相打架
（仿真里这个隐患 2026-09-30 已记为 issue #4）。

- **转场期间**：`move_base` 独占，任务节点绝不发布
- **停靠期间**：任务节点独占（`CmdVelOwner` 线程以 20Hz 持续发布）
- **时序保证**：只在 move_base 的 action result 到达之后才启动 `CmdVelOwner`

**为什么不把 ±90°/180° 也交给 move_base**：goal 的 xy 与当前位置相同时 GlobalPlanner 返回近零长度路径，
TEB 只能纯靠终端 yaw 项旋转 —— 这是最少被走到的分支，失败模式是 ABORT + 恢复行为乱转；
叠加检测位本就贴墙、`min_obstacle_dist` 调大后更易判不可行、每圈 8 次旋转 = 8 次 abort 机会。
→ 旋转由客户端自转器直接发 `/cmd_vel` 完成。

**推论**：`global_plan_overwrite_orientation` 必须 `true`→`false`（原值是为抑制"每个拐角都原地对正"设的，
对"连续样条穿拐角"是对的，对"每个 goal 都是刻意停靠站"是错的）。

### 3. 航向来源分离（照搬仿真会出错的地方）

| 用途 | 来源 | 理由 |
|---|---|---|
| **相对旋转**（±90°/180°） | 真车 `/odom` 的 yaw | 只用差值，坐标系偏置自动抵消；20Hz 低延迟；**不受 AMCL 跳变影响**（旋转时每 90° 约触发 16 次 AMCL 更新） |
| **绝对朝向**（构造 goal） | 表里的 map 系 yaw | 与 `/odom` yaw 差一个 AMCL 拥有的 `map→odom`，**不要假设二者相等** |

`rot_error`/`rot_reached` 两个函数从仿真版**原样复用**（"过冲即停、绝不反向、超时兜底"的语义是对的）。

### 4. 红绿灯关卡做成"停靠点"而非"中途 cancel goal"

中途取消会把车停在任意位置（可能半斜在弯道、灯在相机视野外），而灯本来就该在指定位置读。
→ 每个检测区变成表里 `action: gate` 的停靠点，到达后读灯、红/黄保持并每 1s 重检、绿放行。

**⚠️ 该模式引入的最高危问题**：关卡保持期间没有任何节点在发 `/cmd_vel`。
`newt.py` 若没有指令看门狗，**车会继续执行最后一条 Twist 而溜车**（在停止线/墙前最危险）。
→ `CmdVelOwner` 同时充当 **hold-keeper**：保持期间持续发**零速**，不依赖底盘有没有超时。

### 5. 配置与坐标系适配

| 项 | 仿真 | 真车 |
|---|---|---|
| 雷达 frame | `laser` | **`laser_link`** |
| 相机话题 | `/camera/image_raw` | **`/usb_cam/image_raw`**（launch 加 `image_topic` remap） |
| 地图 | `nav.yaml`（0.05，-6,-6） | `venue_real.{yaml,pgm}`（0.01，-7,-1） |
| `obstacle_range` / `raytrace_range` | 0.5 / 1 | 3.0 / 4.5 |
| `inflation_radius` | 0.1 | 0.40 |
| TEB `min_obstacle_dist` | 0.05 | 0.18（仿真雷达 z≈0.155 看不到地面，真车低装会看到墙根） |
| TEB `yaw_goal_tolerance` | 0.2 | 0.10（检测位要转 ±90° 后相机对准） |
| TEB | — | **`holonomic: true` + `max_vel_y: 0.0`**（先拿全向模型不横移，等 `newt.py` 的 `linear.y` 验证） |

另：`planner_frequency` 0.0→1.0（0.0 是"每个 goal 只规划一次"，只适合无障碍小场地）；
`enable_homotopy_class_planning: false`（TEB 最大 CPU 开销，静态已知走廊无收益）。

## 结果与结论

**已完成（静态校验通过）**：
- `patrol_mission.py` / `patrol_spin_sim.py` py_compile 通过
- 航点表加载与 `yaw_deg: null` 自动解析用桩 ROS 模块跑通（18 个点朝向全部正确）
- 全部 launch XML 良构、全部 YAML / RViz 配置可解析

**未验证**：Windows 上无 ROS，`roslaunch` / `move_base` / 真车**一次都没跑过**。

**两个阻塞项（需人工补齐）**：
1. **真车 footprint 未实测** —— `costmap_common_params.yaml` 与 `teb_local_planner_params.yaml` 两处
   （必须一致），现在还是仿真的 0.34×0.30
2. **真车场地航点未标定** —— 航点表里全是仿真坐标；按 README §10.2 用 RViz `Publish Point` 重新点一遍
   （点记录在 map 系，**车停在哪不重要** —— 这套做法顺带取代了旧 `patrol_green_test.py` 里
   `START_POS_X/Y/YAW` 那个"每次必须停在同一点同一朝向"的刚体变换 hack）

**另一处待核对**：`bringup_drive.launch` 里的驱动节点名（`newt.py`/`pubv.py`/`base_node`/EKF）是按迁移日志写的，
车上 `car_bringup` 的实际包名/launch 名只在车上、仓库里没有，需现场核对。

**验证顺序见 README 第十节**：驱动 bringup → 底盘语义（含 `linear.y` 横移测试）→ 导航栈参数落地
（`rosparam get` 确认）→ AMCL 收敛 → 单个 goal → **贴墙处发"同位置转 90°"验证 TEB 原地旋转** → 逐动作台架 → 完整航线。
