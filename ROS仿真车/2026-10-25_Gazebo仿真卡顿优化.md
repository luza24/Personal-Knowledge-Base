# Gazebo 仿真界面卡顿定位与降载优化

> 整理日期：2026年10月25日 13:08
> 项目：ROS仿真车 ｜ 状态：部分解决 ｜ 标签：`参数调优` `ros` `gazebo` `rviz`

## 背景 / 目标

`roslaunch aic26_bringup bringup.launch mode:=mission backend:=sim` 启动后仿真界面特别卡。
目标：定位卡顿是 CPU、渲染还是显示链路造成的，在不影响实车效果的前提下降低仿真负载，
并把 GUI 精简到只保留 Gazebo 窗口和 RViz。

## 环境信息

- 车端：Ubuntu 20.04 + ROS Noetic，Gazebo **11.15.1**，Intel N100（4 核），7.6 GB 内存
- 工作区：`/home/mowen/aic26_ws_speech`（`feature/speech-announcement`），`ssh vehicle`
- **没有可用 GPU**：`i915` 模块已加载但未绑定设备，`/dev/dri` 不存在，
  `/sys/class/drm/` 里只有 `version`。N100 是 `8086:46d1`（Alder Lake-N），5.15 内核不支持，
  所以 Gazebo 与 RViz 全部走 Mesa 的 **swrast / llvmpipe 软件渲染**
- 远程显示：Windows 上 VcXsrv，车通过裸 TCP 连 `192.168.1.189:6000`
- 无线：车接 **TEST-2.4GHz**（`iw dev wlo1 get power_save` = **on**），电脑在 TEST-5GHz；
  TCP RTT 15–87 ms，Windows→车 ping 均值 50–108 ms（有 259 ms 尖峰）
- 测试期间车上还有另一套 `dingjie_ws` gmapping 栈（`gmapping.launch`，
  wit IMU 节点 ~80% CPU + `slam_gmapping` ~28%），按用户要求未停

## 现象与关键数据（改前）

用原命令复现（12:20 左右），`top -H`、`/gazebo/performance_metrics`、`rostopic hz`、
`ss -tinp` 实测：

| 指标 | 数值 |
|---|---|
| load average | 10–18（4 核） |
| CPU | 94% busy（~6% idle） |
| gzserver | **~230%**，其中 4 个 `llvmpipe` 线程各 ~46%（≈1.85 核） |
| gzclient | ~49% |
| `real_time_factor` | 0.42–0.77，稳态 ~0.56 |
| `/camera/image_raw` | **~2 Hz**（配置 30 Hz，1280×720） |
| X11 客户端 | 5 个：gzclient、rviz、camera_view、mission_controller Tk 面板、day_night 滑块 |
| X11 出流量 | **~7.2 MB/s** |

另外，早前诊断时 `dingjie_ws` 正在 `catkin_make`（两个 cc1plus 各 ~90%），又抢走两个核。

## 根因（按影响排序）

1. **无 GPU，全部软件渲染**：`/proc/<gzserver>/maps` 里只有 `swrast_dri.so`，没有 `iris_dri.so`。
   gzclient 也一样，且 `DISPLAY` 指向远程 X，加重了上下文/交换开销。
2. **1280×720@30 仿真相机是最大单项**：相机传感器在 gzserver 内渲染，
   四个 llvmpipe 线程吃掉近 2 个核，相机实际只能出 ~2 Hz。
3. **CPU 超订**：4 核上同时跑 gzserver + gzclient + RViz + camera_view +
   Tk 结果面板 + 3 个 ONNX 检测节点 + move_base/amcl + mission_controller +
   VS Code server + NoMachine/GNOME，总需求远超 4 核，RTF 掉到 0.5 左右。
4. **画面传输是裸 X11 经 2.4GHz WiFi**：7 MB/s 像素流 + 省电模式带来的 50–100 ms RTT，
   即使渲染出来，拖窗口/转视角也明显滞后。

**结论：降低相机软渲染开销 + 砍掉重复 GUI 能解决 CPU 侧；剩余交互延迟主要来自 WiFi/X11 链路。**

## 修改方案

### 1. 相机参数化

`gazebo_car_union.xacro`：

```xml
<xacro:arg name="camera_image_width" default="1280"/>
<xacro:arg name="camera_image_height" default="720"/>
<xacro:arg name="camera_image_rate" default="30.0"/>
```

`gazebo_camera.xacro`：

```xml
<update_rate>$(arg camera_image_rate)</update_rate>
...
<width>$(arg camera_image_width)</width>
<height>$(arg camera_image_height)</height>
```

`sim.launch` 默认值：

```xml
<arg name="camera_image_width"  default="640"/>
<arg name="camera_image_height" default="360"/>
<arg name="camera_image_rate"   default="15.0"/>
```

并在 `robot_description` 的 xacro 命令后追加
`camera_image_width:=... camera_image_height:=... camera_image_rate:=...`。

### 2. GUI 精简

`bringup.launch`：

```xml
<arg name="show_view"
     default="$(eval 'false' if arg('backend') == 'sim' else 'true')"/>
...
<arg name="gui"
     default="$(eval 'false' if arg('backend') == 'sim' else 'true')"/>
```

`sim.launch` 的 day_night 节点：

```xml
<arg name="day_night_gui" default="false"/>
...
<node pkg="aic26_gazebo" type="day_night.py" name="day_night_gui" ...>
  <param name="gui" value="$(arg day_night_gui)"/>
  <param name="mode" value="$(arg day_night)"/>
</node>
```

### 3. RViz 帧率

`navigation.rviz` 的 `Global Options` 下：

```yaml
Global Options:
  Fixed Frame: map
  Frame Rate: 10
```

实测这项对 X11 流量影响不大（4.6 → 4.2 MB/s），因为 RViz 的流量主要由
costmap/laser 等内容更新触发，而不是纯帧率；保留 10 FPS 主要是省一点渲染 CPU。

## 验证

- `xacro` 默认输出 1280×720、`camera_image_*` 覆盖后输出 640×360：
  用 `xacro src/aic26_description/urdf/gazebo_car_union.xacro` 对比即可
- `roslaunch ... --dump-params`：mission sim 相机 640×360@15；
  capture sim 1280×720@30；real 的 `/mission_controller/gui: true`、
  `camera_view` 参数仍存在（实车行为未变）
- `roslaunch ... --nodes`：sim 下不再有 `/camera_view`
- 实际运行：X11 客户端只剩 gzclient + gzserver（相机离屏上下文）+ rviz；
  `/camera/camera_info` 为 640×360；`/sky_time = 12.0`；日志无 ERROR
- **无需 `catkin_make`**（只改了 launch / xacro / 脚本，devel 里的 Python relay
  会直接执行 `src/aic26_gazebo/scripts/day_night.py`）

### 改后数据

测试时 `dingjie_ws` gmapping 栈仍在跑（约占 1 个多核），因此 RTF 仍偏低：

| 指标 | 改前 | 改后 |
|---|---|---|
| gzserver CPU | ~230%（llvmpipe 4×46%） | **74–83%**（llvmpipe 4×10–16%） |
| gzclient CPU | ~49% | 35–37% |
| X11 客户端 | 5 | **2**（gzclient + rviz） |
| `/camera/image_raw` | 2.0 Hz @1280×720 | **3.25 Hz @640×360** |
| RTF | 0.42–0.77（~0.56） | 0.50–0.63 |
| X11 出流量 | 7.2 MB/s | 6.4 MB/s（gzclient 2.2 + rviz 4.2） |

相机仍未到 15 Hz：llvmpipe 单帧约需 180 ms CPU，受剩余 CPU 竞争限制；
要去掉这个瓶颈只能进一步降分辨率/关阴影，或换有 GPU 的机器。

## 结果与结论

- **CPU 与窗口数已明显改善**：gzserver 从 ~230% 降到 ~80%，不再开 5 个 X 客户端；
  即使多一个 gmapping 栈竞争，相机帧率也从 2 Hz 提到 ~3.3 Hz。
- **实车完全不受影响**：`backend:=real` 使用 `/dev/video0` 与独立的
  `camera_width/camera_height/camera_fps`（1280×720@30），本次只改 Gazebo 仿真传感器；
  decision/perception/utils/slam 中无 1280/720 硬编码，检测器输入本来 letterbox 到 640。
  `mode:=capture` 强制 1280×720@30。
- **剩余卡顿主要在显示链路**：6.4 MB/s 裸 X11 经 2.4GHz + `power_save: on`。
  未改代码的建议：
  ```bash
  sudo iw dev wlo1 set power_save off
  nmcli connection modify TEST-2.4GHz 802-11-wireless.powersave 2
  ```
  并尽量让车连 TEST-5GHz；若仍不够，再考虑 NoMachine 虚拟桌面（压缩传输）。
- 备份：`/home/mowen/aic26_ws_speech_backups/pre_simperf_20261025/`
  （含 `pre_simperf.patch`，以及 `navigation.rviz`、`day_night.py` 原件）
- 改动未提交；测试用的仿真已停止，11311/11345 空闲，另一套 gmapping 栈未触碰。
- 启动命令不变：
  ```bash
  roslaunch aic26_bringup bringup.launch mode:=mission backend:=sim
  ```
