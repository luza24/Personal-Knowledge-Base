### A 已接受的回归

1. **真车 footprint 变小**：0.315×0.285（8 点）→ 0.284×0.272（固定 4 点）；
   宽度少 3.1 cm、高度少 1.3 cm，轮子外沿横向每侧少约 6.5 mm，窄道余量下降。
2. **激光距离修复丢失**：根节点 `obstacle_range/raytrace_range` 在 ObstacleLayer 中
   可能被忽略，回退到 2.5/3.0；真车 4 m 激光超出 3 m 的旧障碍无法清除。
3. **GlobalPlanner 参数失效**：双重命名空间；插件回退 `cost_factor=3`、
   `default_tolerance=0`，路径更贴墙/切内角，靠墙航点可能规划失败。
4. **costmap 刷新/膨胀回退**：障碍显示/清除更滞后，安全余量略降。
5. **TEB 窄道/终点回退**：0.50 m 走廊单侧最大余量约 0.1075 m，小于 0.12 m；
   可能蠕行/拒绝轨迹；`global_plan_overwrite_orientation=true` 可能让终点反复微调。
6. **不重新引入旧 `rotate_to` bug**：decision 的误差符号/减速修复、`turn_min_speed`、
   fail-closed `wait_ready`、`check_environment` 都保留。
7. **A 不修复 `real_waypoints.yaml` 的 yaw 未实测问题**，也不保证转向偏差变好。

## 任务点转向偏差排查

### 1. 线程阻塞结论

**没有发现 move_base 被单个线程死锁/卡死**。当前 11312 的仿真：

- move_base 11 个线程，其中 1 个线程持续 **99.9% CPU（R 状态）**，其他线程睡眠；
- 没有 D 状态进程、没有 futex/IO 死锁迹象；
- 但 action feedback 只有 **~5.8 Hz**（配置 `controller_frequency=10`），
  `/cmd_vel` 只有 **~2.7 Hz**，12 秒采样全 0；
- load average 在 4–10 波动，gzserver ~47%、VS Code ~41%、move_base ~55–82%。

结论：更像 **CPU 调度饥饿/控制循环跑不满**，不是死锁。实车测试时若车上还跑仿真，
实车节点会被同样拖慢；`check_environment()` 只能发现同一 master 的
`/chassis`+`/gazebo`，发现不了另一个 master 上的仿真。

### 2. 实车/仿真日志

- 唯一一份实车任务日志是 **10/23 19:41–19:43**：`/cmd_vel` 连 `/chassis`，
  GUI 被禁用；转向完成，90° 约 5.2 s，没有 rotate timeout 或串口错误；
  最后 car_1 是手动 Ctrl+C 结束。该版本早于当前 `rotate_to` 修复，不能代表现在。
- 10/24 21:54 的任务日志是**仿真**（`/cmd_vel` 连 `/gazebo`，GUI 开启），
  90°/180° 转向约 8–11 s，只能说明仿真里控制循环被拖慢。
- 10/23 底盘日志 `chassis: opened /dev/carserial at 115200`，运行中无串口错误。

### 3. 最可能的偏差来源（排序）

1. **`real_waypoints.yaml` 的 yaw 未实测**：文件头部明确写“目前照抄仿真场景，
   需要现场实测”；任务点目标角 = `wp.yaw ± 90°`，yaw 错会导致系统性偏差。
2. **两个 `/cmd_vel` 发布者**：move_base + mission_controller（demo 里是 demo_cycle）。
   chassis 回调只保留最后一条，转向时可能互相覆盖。
3. **停止/过冲**：`rotate_to` 到容差后只发一帧零速度，然后
   `turn_settle=0.5s`；chassis `cmd_timeout=0.5s`。零速度帧丢失/被覆盖时，
   车可能继续以最后速度走最多 0.5 s，0.8 rad/s × 0.5 s ≈ 23°。
4. **底盘串口路径潜在阻塞**：`_send_command` 和 `_read_loop` 共用一个 pyserial
   对象且无显式锁；`write_timeout=0.5`、`write()+flush()` 可能阻塞。
   实车日志未见串口报错，属待验证项。
5. **CPU/GUI/GIL**：`gui:=true` 时 ResultViewer 订阅三路图像并在回调里
   `cv2.imwrite`；在 N100 上会增加负载。10/23 实车日志 GUI 是禁用的，
   所以那次不是 GUI 导致；当前仿真 GUI 是开启的。

### 4. 建议的下一步

1. 停掉 11312 上的 headless demo（不是本会话启动，未擅自杀）。
2. 选一个任务点，用 `gui:=false show_view:=false use_rviz:=false` 复现；记录：
   - `rostopic hz /cmd_vel`（转向时接近 20 Hz，move_base 导航时约 10 Hz）
   - `rostopic hz /move_base/feedback`
   - `top -H` 看 move_base / mission_controller / chassis 线程
   - `rostopic echo -p /cmd_vel` 看 0/非 0 交替与间隔
   - `/vel_raw` 或 `/odom` 确认底盘收到并执行
   - `tf_echo map base_footprint` 与停稳后的实际 yaw
3. 先实测并更新 `real_waypoints.yaml` 的 yaw，并确认 `real_tasks.yaml`
   的 turn left/right 方向。
4. 如果 `/cmd_vel` 能到 20 Hz 但车仍过冲：查停稳后的最终误差、chassis 停止延迟、
   双发布者；必要时加 cmd_vel mux 或零速度 burst。
5. 如果 `/cmd_vel` 一直很低：查 mission 线程/GIL、move_base CPU、GUI 负载。

## GUI 显示（同次对话的附带成果）

- 原因：`backend:=real` 不启动 Gazebo（Gazebo 只在 sim）；RViz/相机/结果面板需要
  `DISPLAY`，而车端无显示器、`DISPLAY` 为空。
- 在 `aic26_bringup/launch/bringup.launch` 增加 `gui_display`：
  优先用已有 `DISPLAY`（NoMachine/ssh -Y），否则用 `SSH_CLIENT` 的客户端 IP + `:0.0`
  （Windows VcXsrv，TCP 6000）。
- 已验证 VcXsrv 直连 `192.168.1.189:6000` 和 SSH 反向隧道都能用；
  RViz 可稳定运行；Gazebo GUI 在独立端口验证可启动。
- 工具：`src/aic26_bringup/tools/{run_gui_real.sh,run_gui_sim.sh,README_GUI.md}`、
  `tools/windows/*.cmd`、桌面 `start_vcxsrv.cmd`；
  启动器会拒绝在已有 aic26 栈/Gazebo 占用时启动。
- 注意：当前 11312 上仍有 headless demo，默认端口测试前要先停掉。
