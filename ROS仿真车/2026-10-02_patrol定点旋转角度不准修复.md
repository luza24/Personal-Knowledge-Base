# patrol 脚本定点旋转角度不准（开环改地面真值闭环）

> 整理日期：2026年10月2日 19:28

## 环境信息
- 运行环境：Docker 容器 `ros_noetic_gazebo`（镜像 `osrf/ros:noetic-desktop-full`），ROS1 Noetic
- 底盘：四轮**滑移转向**（`libgazebo_ros_skid_steer_drive.so`，见 `src/aic26_description/urdf/gazebo_car_union.xacro`）
- 巡逻脚本：`src/aic26_navigation/scripts/patrol_green_test.py`（含旋转点/任务点定点转向逻辑）

## 报错记录
- **现象**：小车在任务点 1 `(1.10,-1.45)`、任务点 2 `(1.10,-0.5)` 处向右定点旋转后，实际转角**偏差约 45°**（应转 90°）。
- **根因**：旋转采用**开环固定时长** `TASK_ROTATE_DURATION = TASK_ANGLE / TASK_W = (π/2)/0.8 ≈ 1.96s`。滑移底盘原地转向打滑，实际车体角速度约 0.5 rad/s（低于命令 0.8），固定转 1.96s 实际只转过约一半角度。
- 代码注释已写明「odom 打滑不可信」：滑移转向插件的 `/odom` 是按命令速度积分出来的、与物理脱节，不能用它做旋转闭环。

## 涉及文件
- `src/aic26_navigation/scripts/patrol_spin.py`（唯一改动文件）
## 修改方案
把「开环转固定时长」改为「**读 Gazebo 地面真值 yaw 做闭环**」，转到目标角度才停：
1. 新增订阅 `/gazebo/model_states`（`gazebo_msgs.msg.ModelStates`），回调 `gt_cb` 取 `armbot` 的真实 yaw（复用 odom_cb 的四元数→yaw 公式）。
2. 新增判定函数 `yaw_reached(cur, start, target, tol=ROT_TOL)`，容差 `ROT_TOL=0.05`（约 3°）。
3. 四个旋转态全部改闭环：任务点右转 90°（target=-π/2）、旋转点左转 90°（target=+π/2）、以及各自的「转回原方向」（target=0，回到 start_yaw）。
4. 保留**超时兜底** `SPIN_ROTATE_TIMEOUT / TASK_ROTATE_TIMEOUT = 3.0 × 原固定时长`，防止地面真值话题异常时车原地打转。
5. 每次进入旋转态时记录起始真值 yaw：`spin_start_yaw` / `task_start_yaw`。

## 结果与结论
- **部分解决**：闭环代码已部署、语法通过、`gazebo_msgs` 可用、地面真值话题 `/gazebo/model_states` 以 ~1000Hz 稳定发布且含 `armbot`。
- **闭环确实生效**：日志显示转 90° 从固定 1.96s 变为「转到位才停」的 ~3.1s（对应打滑后的真实角速度）。
- **遗留问题**：**「任务点转回原方向」仍稳定走超时兜底**（用 6~7s = 5.9s 超时 + 余量），导致转回后角度不准；而「旋转点转回」正常（3.5s 闭环成功）。两者唯一区别是转回方向——旋转点转回=顺时针（+90°→0），任务点转回=逆时针（-90°→0）。
- **未完成实测定位**：排查过程中仿真环境（rosmaster + gazebo）被关闭，未能抓取「任务点转回」阶段的完整 yaw 轨迹来判定是「逆时针打滑越界」还是「基准 yaw 漂移」。`yaw_reached` 的数学已通过模拟验证无误。

### 待办
- 需在仿真运行时抓取「任务点转回」的 yaw 曲线，确认是越界/漂移后精确修复；或先上保守修复（放宽转回容差 + 加「已转过足够角度」双重条件）。

## 附：2026-10-04~05 后续重构与调试（patrol_spin.py）

> 承接上文遗留问题，后续多轮调试与重构最终把巡逻脚本演进为 `src/aic26_navigation/scripts/patrol_spin.py`（642 行）。关键结论与改动如下。

### 1. 旋转「转超」真根因：重构时参数被误改（不是打滑/wrap）

- 现象：用户报告任务点向右旋转**超过 90°**，看似转了 180°~360°。
- 反复排查（打滑、`normalize_angle` 在 ±π wrap、`atan2` 跳变等）均无法复现，实测三次（start_yaw=0 / 3.0 / -3.0）都精确转 90° 停。
- **真根因**：之前把全局变量重构为类时，误改了 6 个参数值——`MAX_W/SPIN_W/TASK_W` 0.8→0.5、`SPIN_WAIT` 2.0→1.0、`TASK_WAIT` 3.0→1.0、任务点1 y 坐标 `-1.45`→`-1.10`，加上 `TASK_ROTATE_TIMEOUT` 少了 `3.0*`。恢复后转 90° 精确正常。
- 教训：重构"照搬常量"要逐值核对，git diff 是定位这类问题的利器。

### 2. `yaw_reached` 改为「过冲即停」语义

- 原「精确相等」判断在打滑跳过 tol 窗口后、±π wrap 会永远失配导致转到超时。
- 改为：`target>0` 判 `diff >= target-tol`（左转过冲也停）、`target<0` 判 `diff <= target+tol`（右转过冲也停）、`target==0` 判回到 start（容差内）。

### 3. 旋转方案 D：PID 比例减速

- 新增 `rot_error(cur, start, target)` 返回剩余旋转角（带符号）+ `ROT_KP=2.0`。
- 旋转从「满速 0.8 + 判停」改为 `cmd.angular.z = clamp(ROT_KP * err, -MAX_W, MAX_W)`，接近目标自动减速，抑制滑移底盘打滑，转完朝向更准。

### 4. 车牌识别区（PlateScanZone）与拐弯冲突

- 新增 `PlateScanZone`（目标点 `(0.8,-1.70)`，半径 0.2，只检测一次）+ `YoloClient.detect_plates`（解析 `plates` 数组打印车牌号）。
- **冲突根因**：`detect_plates` 调 `/yolo/detect` 是**同步阻塞**（100~200ms），识别区离拐弯点 `(1.05,-1.70)` 仅 0.25m，阻塞卡在拐弯前导致车冲过头来不及转向。
- **修复**：改为 `threading.Thread(..., daemon=True).start()` 后台异步执行，`update()` 立即返回（实测 0.000s），主循环 20Hz 不再卡顿。

### 5. 终点掉头 + 检查点保护

- 需求演进：巡逻只走 LOOP_A 一次 → 到达最后一点 `(1.75,1.75)` → **原地 180° 掉头**停住。
- 新增 `ParkingAction`（none → uturn → done），掉头用 PID 减速转 `+π`。
- `WaypointFollower` 改为开放路径（`n_pts=len(loop)`，最后一点不再前进）。
- **检查点保护**：车 spawn 在 `(1.7,1.7)`，与终点 `(1.75,1.75)` 仅差 0.07m，会误判终点。新增 `CHECKPOINT=(1.05,-1.70)` + `passed_checkpoint` 标志，必须经过检查点后才允许终点判定。
- **只转一次**：`ParkingAction.start()` 加 `if state != none: return` 保护，重复调用不重置。

### 最终 patrol_spin.py 结构
- 函数：`normalize_angle` / `yaw_reached` / `rot_error`
- 类：`YoloClient`（detect_objects/detect_light/detect_plates）、`SpinAction`（左转90°）、`TaskAction`（右转90°）、`PlateScanZone`（车牌识别）、`TrafficLightGate`（红绿灯停车）、`ParkingAction`（终点180°掉头）、`WaypointFollower`（waypoint跟随）、`PatrolNode`（编排）
- 路径：仅 `LOOP_A_RAW`（10 点，起点 `(1.13,1.7)`，终点 `(1.75,1.75)`），已删 `LOOP_B_RAW`。

## 附：2026-10-10 代码回溯核查：车牌识别区转向有误 ⇄ 线程阻塞

> 承接上文第 4 节（车牌识别区与拐弯冲突），对 `aic26 10.08代码` 工作区做一次代码回溯，确认该问题在 `patrol_spin.py` + `aic26_perception` 中的落地方式。**本次为分析核查，未产生新的代码改动。**

### 核查环境
- 代码工作区：`C:\Users\luza\Desktop\aic26 10.08代码`（Windows 侧代码副本）
- 关键文件：
  - `aic26_navigation/scripts/patrol_spin.py`（巡逻主节点，20Hz 主循环）
  - `aic26_perception/scripts/yolo_detector.py`（服务式检测节点，提供 `/yolo/detect`）
  - `aic26_perception/scripts/vision_utils.py`（OCR/匹配/编解码公共模块）

### 结论：是，根因就是线程阻塞——OCR 同步调用卡死 20Hz 主循环
- **阻塞源**：`/yolo/detect` 是**同步 ROS 服务**，YOLO 推理 + RapidOCR 全在服务端串行执行；车牌 OCR 单次可达数秒（懒加载 + 多档拉伸重试）。
- **放大点**：车牌识别区目标 `(0.8,-1.70)`、半径 0.2，而路径在该处是 `(-0.05,-1.70)→(1.05,-1.70)→(1.13,1.75)`，**距拐点 `(1.05,-1.70)` 仅 0.25m**。识别触发的那一拍正是该急转的那一拍；一旦主循环在循环体内同步 `proxy()` 阻塞数秒，期间不发布 `/cmd_vel`，车带上一条指令冲过路口 → **来不及转向**，即「车牌识别区转向有误」。

### 修改方案（已在代码中落地，本次逐条核对）
1. **车牌识别异步化**（对应本问题）：`PlateScanZone.update`（`patrol_spin.py:367-375`）改为 `threading.Thread(target=self.yolo.detect_plates, daemon=True).start()`，`update()` 立即返回，主循环 20Hz 不被卡；注释即写明「不阻塞主循环(避免拐弯处来不及转向)」。
2. **目标检测异步化**：`YoloClient.detect_objects`（`:150-183`）同样起后台线程跑 `proxy()`，用 `self._lock` 保护计数桶累加（`:173-177`），线程句柄存入 `_detect_threads`，收尾 `wait_detections()`（`:185-189`）统一 join，保证 A/B 社区人数统计完整。
3. **旋转「先停车再检测」**：`RotateAction.update`（`:315-333`）在进入 detect 态时先 `cmd=0` 停稳，注释「先停车, 再检测(避免同步阻塞期间车多转)」——用顺序化解掉残留阻塞的影响。
4. **旋转闭环修正**（另一类「转向有误」，与阻塞无关，一并确认）：改用 `/gazebo/model_states` 真值 yaw 而非滑移底盘 `/odom`（`:540-552`）；`rot_reached` 过冲即停语义（`:41-58`）；到位后反向刹车 `BRAKE_W/BRAKE_DURATION`（`:324-325`）抵消无阻尼惯性溜车。
5. **感知侧配合**：`yolo_detector.py` 用 `infer_lock` 串行化推理（`:84,:120`），避免后台多线程并发打服务导致模型并发执行；启动时 `self.model(zeros)` 预热（`:80`）+ 预加载 RapidOCR（`:74`），把冷启动数秒提前到节点启动阶段。
6. **有意保留的同步点**：`TrafficLightGate.update`（`:404-423`）仍同步调 `detect_light()`，但调用前先 `self.pub.publish(Twist())`（`:404`）把车停下、其后 `cmd` 恒为 0，阻塞期间本就该停车，故可接受。

### 遗留小隐患（未改，仅记录）
- `YoloClient.detect_plates` 写 `self.last_matched`（`patrol_spin.py:225`）未加锁；当前无并发读，暂不影响，若后续要读需补 `self._lock`（`detect_objects` 已有锁，`detect_plates` 没有）。
