# 容器显示后端卡在 local：Gazebo/RViz 不出窗口排查

> 整理日期：2026年10月15日 22:42
> 项目：开发环境 ｜ 状态：已解决 ｜ 标签：`报错排查` `docker` `wsl2` `ros`

## 背景 / 目标

容器 `ros_noetic_gazebo` 里跑 `roslaunch aic26_gazebo aic26-1.launch`，**Gazebo 窗口不出现**，
Windows 桌面什么都没有。

## 环境信息

- Windows 11 宿主机 + Docker Desktop / WSL2；容器 `ros_noetic_gazebo`（`osrf/ros:noetic-desktop-full`，`--network host`）
- 容器内 `/root/display.sh`：三后端管理器（`external` > `windows` > `local`），全部服务 `DISPLAY=:0`
- Windows 侧 X server：VcXsrv

## 报错记录 / 现象

容器里所有 GUI 程序（Gazebo、RViz）都渲染不出来，Windows 桌面上没有任何窗口，
但进程正常、无报错。

## 排查

```bash
docker exec ros_noetic_gazebo bash -lc "/root/display.sh status"
```

```
  xvfb      运行中 (pid 83)
  x11vnc    运行中 (pid 100)
  noVNC     运行中 (pid 130)
  socat     未运行              ← 关键

  :0           : 可用 (本脚本的 local 后端在服务)
  当前后端     : local          ← 关键
  Windows X    : 可达 (host.docker.internal:6000 = 192.168.65.254)
```

再看 Windows 侧：

```bash
tasklist | grep -i vcxsrv          # vcxsrv.exe pid 14368 在跑
netstat -ano | grep ":6000"        # 0.0.0.0:6000 LISTENING, pid 14368 —— 正是 :0, 正确
```

## 根因

**后端卡在 `local`（容器内 Xvfb），而它本该用 `windows`（socat 转发到 Windows VcXsrv）。**

GUI 渲染进了容器内那个**看不见的 Xvfb 虚拟屏**，所以 Windows 桌面什么都不显示。

**⚠️ 注意这与已知的那个坑是【不同变体】：**

| 已知变体（2026-10-02） | 本次变体（2026-10-15） |
|---|---|
| VcXsrv 被 `-displayfd` 自动选号跑到 `:1`（6001）→ 探测 `:6000` 失败 → 回退 `local` | **VcXsrv 正确监听 `:0`、容器也够得着**，但后端**仍然是 `local`** |

原因：`display.sh` 是在**启动时**探测一次并把结果写进 `MODEFILE` 的
（`elif alive xvfb; then echo local > "$MODEFILE"`）。
**只要探测那一刻 VcXsrv 还没起来（或 6000 还没监听），就会落到 `local`，之后再也不重探。**

### 2026-10-16 再次复现：拿到了时间线的直接证据

第二天同一现象又出现（容器里没改过任何显示配置）。这次把两侧的启动时刻拉出来对：

| 时刻（本地） | 事件 | 取证命令 |
|---|---|---|
| 19:38:29 | 容器启动，`display.sh` 自动探测 6000 → 失败 → 落 `local` | `docker inspect --format '{{.State.StartedAt}}'` |
| 20:00:03 | 用户才启动 VcXsrv | `Get-CimInstance Win32_Process -Filter "Name like '%vcxsrv%'"` |
| 20:02 | 排查时 `status`：`当前后端: local` + `Windows X: 可达` | `/root/display.sh status` |

**VcXsrv 比容器晚起 22 分钟** —— 上面那条机制就此坐实：探测那一刻 6000 没人监听，
直接进 `local`；之后 VcXsrv 起来了也不重探。

补充一条容易误判的：**光重跑一遍 `display.sh`（不带参数）也救不回来** ——
`start|auto` 分支有意不切换已经在跑的后端（脚本注释写明：切换会先 `stop_local`
把正在跑的 Gazebo 弄挂）。必须显式 `display.sh windows`。

**复发隐患**：这次的 VcXsrv 命令行是 `vcxsrv -multiwindow -clipboard -wgl -displayfd 668` ——
带 `-displayfd`，**显示号是自动挑的、不固定**。这次 6000 空着所以落在 `:0` 纯属运气；
哪天 6000 被占就会跳到 `:1`，又回到 2026-10-02 那个变体。根治办法是固定显示号：

```
"C:\Program Files\VcXsrv\vcxsrv.exe" -multiwindow -clipboard -wgl -ac :0
```

（去掉 `-displayfd`、`:0` 显式指定、`-ac` 关访问控制。XLaunch 等价：Display number 填死 `0`。）

## 次因：`local` 后端的浏览器逃生口也是断的

`local` 后端的设计是用 `http://localhost:6080/vnc.html` 看画面。实测从 Windows：

```
Test-NetConnection localhost -Port 6080 → False
```

连不上。因为容器是 `--network host`，**Docker Desktop 在这种模式下不把容器端口发布到 Windows**
（容器→Windows 方向通，反方向不通）。而且 `x11vnc` 带 `-localhost`，只监听 `127.0.0.1:5900`，
容器外更够不着。

→ **画面进了隐形屏，浏览器后路又断了，两边都看不到。**

## 修改方案

```bash
docker exec ros_noetic_gazebo bash -lc "/root/display.sh windows"
```

脚本会先 `stop_local`（Xvfb 占着同一个 socket 路径 `$XSOCK`，不停掉 socat 绑不上），
再起 socat 把 `/tmp/.X11-unix/X0` 转发到 `host.docker.internal:6000`。
它自带前置检查（显存可达性、socket 目录可写、转发后 `x_alive` 探测），
本次这几项 status 显示全部通过，一次成功。

## 结果与结论

**已解决。** 切换后：

```
  socat     运行中 (pid 39411)
  当前后端     : windows
  Windows X    : 可达 (host.docker.internal:6000 = 192.168.65.254)
```

起 Gazebo 验证窗口**确实映射到了 VcXsrv**：

```bash
docker exec ros_noetic_gazebo bash -lc 'xwininfo -root -tree | grep -i gazebo'
#  0x400010 "Gazebo": ("gazebo" "gazebo")  1711x1048+0+0  +0+0
```

`xwininfo -root -tree` 查的是容器里的 `:0`，切换后它就是 socat → VcXsrv，
所以这里查到窗口 = 窗口真的在 Windows 侧存在。

**切回 `local`**：`docker exec ros_noetic_gazebo bash -lc "/root/display.sh local"`
（但切回去就又看不到窗口了，因为 6080 从 Windows 连不上）。

**2026-10-16 补充：一个更强的端到端验证法 —— 两端比对窗口 ID。**

上面 `xwininfo -root -tree` 查的是**容器里的** `:0`，属于间接证明：
它成立的前提是"容器 `:0` 已经等于 socat → VcXsrv"。更直接的办法是两端各查一次、看是不是同一个窗口：

```bash
docker exec ros_noetic_gazebo bash -lc 'DISPLAY=:0 setsid xclock -geometry 200x200+50+50 >/dev/null 2>&1 </dev/null &'
sleep 3
docker exec ros_noetic_gazebo bash -lc 'xwininfo -display :0 -root -tree | grep xclock'
# → 0x20000a "xclock": ...
docker exec ros_noetic_gazebo bash -lc 'xwininfo -display 192.168.65.254:0 -root -tree | grep xclock'
# → 0x20000a "xclock": ...     同一个 ID = 管道确实通了
```

两个要点：`-display` 要写**宿主 IPv4**（`192.168.65.254`），
写 `host.docker.internal:0` 会解析出 IPv6 而连不上；
用 `xclock` 而不是 Gazebo，是因为它起停只要 3 秒，可以反复验，不必每次都等仿真加载完。

## 踩坑记录

**1. `pkill -f` 会匹配到自己的命令行 —— 自杀**

```bash
docker exec ros_noetic_gazebo bash -lc 'pkill -f "roslaunch aic26_gazebo"'
```

这条命令**把自己的 bash 也杀了**（模式串就写在命令行里，`-f` 匹配整条 cmdline），
表现是命令挂住 2 分钟才以 exit 143 返回。

正确写法 —— 用字符类打断自匹配：

```bash
pkill -f "[r]oslaunch aic26_gazebo"
```

**2. 只停 gazebo 会让整个 ROS 会话连锁退出**

如果被杀的 `roslaunch` 恰好持有 `rosmaster`，master 一没，其余节点
（amcl / move_base / rviz / perception…）**全部随之退出**。
所以"只重启 Gazebo"往往做不到——重启时仿真时钟从 0 开始，
而还活着的 AMCL/move_base 攥着旧时钟和旧 TF，两边对不上。
**要重启就整套一起重启。**
