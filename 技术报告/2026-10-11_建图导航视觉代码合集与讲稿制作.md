## 报错记录

1. **docx 改写后段落错位（讲稿内容丢失 + 串位）**
   - 现象：第 2 段仍是旧文本、第 3 段变成了本该属于第 2 段的新文本、末尾两段（视觉检测 / 视觉算法）整段消失。
   - 根因：遍历段落时写了 `if '<w:t' not in p: new_paras.append(p); continue` —— **空段落在 `continue` 之前没有执行 `idx += 1`**，导致后续段落索引整体前移一格，`T[idx]` 全部错位一格。
   - 触发条件：文档中存在空段落（本例第 2 段为空行）。

2. **拆段后段落对齐失败**
   - 现象：`assert len(new_paras) == len(paras)` 失败。
   - 根因：把「视觉检测 + 视觉算法」合并的一段拆成两段后，`new_paras` 比 `paras` 多 1 项；替换循环用 `zip(paras, new_paras)` 逐一对齐，长度不等必然错位。
   - 修法：拆段时把两段 XML **拼成一个字符串**再替换原段，保持 1:1。

3. **写盘 `PermissionError: [WinError 5] 拒绝访问`**
   - 现象：`os.replace(tmp, dst)` 失败。
   - 根因：桌面是 OneDrive 同步目录，且 WPS/Word 可能正打开该文件（即使没有 `~$` 锁文件也会短暂占用）。
   - 修法：把 `os.replace` 包在 5~6 次重试里、每次 `time.sleep(2)`，随后成功。

4. **Git Bash heredoc 传含中文的 Python 源码报编码错**
   - 现象：`python - <<'PYEOF'`（脚本内含中文）报 `SyntaxError: Non-UTF-8 code starting with '\xe5' in file <stdin> ... no encoding declared`。
   - 根因：MSYS 把 heredoc 内容按本地编码（GBK/cp936）写入 stdin，中文不再是 UTF-8。
   - 修法：改用 Write 工具写 `.py` 文件（UTF-8）再执行；脚本首行加 `# -*- coding: utf-8 -*-`。

5. **用户反馈「讲稿没了」（实为虚警）**
   - 核查结果：`讲稿.docx` 仍在桌面；`zipfile.testzip()` 通过、`document.xml` 可被 `ElementTree` 解析、16 个部件齐全、`[Content_Types].xml` 为首条目 —— **文件本身完好**，判断为打开时的显示/缓存问题。
   - 处置：按用户要求从零重建一份标准 docx。

## 附：`/odom` 「按命令速度积分、与真实物理脱节」的逻辑

> 该主题的完整上下文见 `patrol脚本定点旋转角度不准修复_2026年10月2日_10月10号修改.md`。

- `/odom` 的数据源是 `/cmd_vel`（**指令**），插件按 `θ += ω·dt`、`x += v·cosθ·dt` 积分出位姿 → 它回答的是「**如果车照我说的动，它在哪**」，而不是「车实际在哪」。
- `/gazebo/model_states` 取自物理引擎里模型的实际位姿 → 这才是「车实际在哪」。
- 两端脱节的机制：**积分的输入是指令，中间不读回物理结果**。指令与实际的任何差异（滑移底盘原地转向的横向刮擦打滑、被障碍挡住、碰撞）都会 1:1 变成里程计误差 —— 打滑越严重，`/odom` 虚报越多。
- 现象印证：命令 ω=0.8 转 1.96 s，`/odom` 认为已转 90°，实际车体只转了约 45°；用 `/odom` 做旋转闭环就会提前判「到位」。
- 副作用：用 `/odom` 评估性能**看不出打滑代价**（因为它假设没打滑），该代价只会在真车（麦克纳姆轮 + 轮式里程计）上暴露。
