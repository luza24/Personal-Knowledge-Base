# 实车 traffic_2_north 门口卡顿：航点格角与退避进墙

> 整理日期：2026年11月15日 19:21
> 项目：ROS仿真车 ｜ 类型：报错排查 ｜ 状态：部分解决 ｜ 主题：`导航与运动控制` ｜ 标签：`ros` `move_base` `teb` `真车`

## 背景 / 目标

实车 passable 分支在 `corner_3_to_traffic`（goto）之后、或下一节点处会卡住约 15–25 s，随后又“自己恢复”继续走。目标是判断卡在哪个节点、为什么规划失败，并用**只改任务坐标点**的方式修复。

## 环境信息

- `/home/mowen/aic26_ws_112`，`bringup.launch backend:=real`，`config_prefix=real_nostrafe`。
- 地图 `world_real.pgm`：224×224，0.05 m，origin (-6,-6)，大部分 unknown；`track_unknown_space: false`。
- 虚拟墙 `virtual_walls.yaml`：中央走廊 x=-0.42 / x=0.22（中心线 0.64 m），南门口 y=-1.36 分成 x[-1.37,-0.41] 与 [0.21,0.77]，唯一开口约 0.62 m。
- 真实足迹 0.285 m 宽（内切 0.1425）；全局膨胀 0.26 / 3.5，局部 0.18 / 5.0；TEB `min_obstacle_dist 0.08`、`inflation_dist 0.16`；`disable_strafe=true`（横移关闭）。
- GlobalPlanner：`use_dijkstra true`、`use_quadratic true`、`use_grid_path false`（GradientPath）。

用户观察的“卡约 20 s 又正常前进”对应：12 s 无进展 → 退 0.12 m（约 4 s）→ 重发目标；11/13 重试成功，11/14 则是放弃该节点继续下一任务。

## 根因分析

1. **起点正好在 0.05 m 网格角点。** `corner_3_to_traffic=(-0.1,-1.65)` 的网格坐标是 `(118.0, 87.0)`；目标 `traffic_2_north=(-0.1,-0.1)` 是 `(118.0, 118.0)`。`use_grid_path:false` 走 GradientPath 的亚格插值，在这个位置取路失败，即使 potential 合法、costmap 实际连通（离线 BFS 已验证连通）。
2. **12 s 后的自动退避把车尾送进墙边。** 从 `-1.65` 退到 `-1.77`，车尾 `-1.955` 距南侧外圈虚拟墙只剩 0.07–0.075 m，低于 TEB `min_obstacle_dist 0.08`，于是重试阶段 TEB 从非法位姿起步，连续报 `trajectory is not feasible`。
3. **门口本身不是不可通过。** 有效 <253 通道约 0.40 m，车宽 0.285 m，居中两侧各约 5.7 cm；LETHAL 净开口约 0.60 m。主要矛盾是格角起点与退避位置，而不是门口宽度。
4. `sign_gate` 检测超时后默认走 passable（这次的分支），blocked 分支走西侧 `corner_3_to_w`，不经过这个门口。

## 修改方案

按用户要求只改坐标，不动规划器、膨胀、虚拟墙、退避逻辑和横移：

```yaml
  - name: "corner_3_to_traffic"
    x: -0.075      # was -0.1
    y: -1.525      # was -1.65
    yaw: 1.570796
    dwell: 0.0

  - name: "traffic_2_north"
    x: -0.075      # was -0.1
    y: -0.075      # was -0.1
    yaw: 1.570796
    dwell: 0.0
```

依据：

- 两点的 `(x+6)/0.05`、`(y+6)/0.05` 小数部分都是 **0.5**，是真正的格心，消除 GradientPath 角点歧义。
- 新车尾 `y=-1.71`，距南墙 **0.300 m**；即使触发默认 0.12 m 退避，车尾仍留 **0.200 m**（阈值 0.08）。
- 车头 `y=-1.3675`，位于开口内，距两侧墙端横向 ≥0.15 m；纯 goto，无检测取景/播报语义。

本次明确不改：`use_grid_path`（仍为 false）、costmap 膨胀、TEB 参数、虚拟墙宽度、`mission_common.py` 退避/重试、底盘横移（`disable_strafe=true` 保持）。

后备方案：若实车仍偶发 `NO PATH!`，再单独把 `global_planner_params.yaml` 的 `use_grid_path` 改成 `true` 做 A/B。

## 验证

离线复算（地图 + 16 段虚拟墙 + 0.1425 内切膨胀）：

- 新起点/目标均为格心；两者 <253 通道 BFS 连通（visited 1825 cells）。
- 车尾 0.300 m、退 0.12 m 后 0.200 m；门口有效通道约 0.400 m。

实车验证（待做）：

```bash
roslaunch aic26_bringup bringup.launch backend:=real
# 跑 passable 分支后
L=~/.ros/log/latest
grep -c "NO PATH!" $L/rosout.log
grep -c "not feasible" $L/rosout.log
grep -E "task: (corner_3_to_traffic|traffic_2_north)|backing off|failed to reach traffic_2_north" \
  $L/mission_controller-*.log
```

验收：前两项均为 0；两个 `task:` 相邻，无 `backing off`、无 `failed to reach`；重复 3 次一致。

单点复现（可选，车已摆到新起点）：

```bash
rostopic pub -1 /move_base_simple/goal geometry_msgs/PoseStamped \
'{header: {frame_id: "map"}, pose: {position: {x: -0.075, y: -0.075, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.7071068, w: 0.7071068}}}'
```

只发一次，不要 `-r`；建议同时记录 `/tf /scan /odom /amcl_pose /move_base/GlobalPlanner/plan /move_base/global_costmap/costmap /move_base/local_costmap/costmap /cmd_vel`。

## 结果与结论

- 坐标已修改并写入 `WORKSPACE_STATE.md`，离线几何校验通过；**尚未实车复跑**，状态“部分解决”。
- 预期效果：第一次规划即成功，原来的 15–25 s 卡顿归零；即使仍触发重试，退避后也不会再进墙。
- 若实车仍失败：先看是否仍为 `NO PATH!`（转 `use_grid_path:true`）；若变成 TEB infeasible，再把起点退到 `y=-1.575`（仍格心，车尾余量 0.266 m）或考虑放宽虚拟墙开口。
- 回滚：`cp -p real_nostrafe_waypoints.yaml.bak_20261115_gate real_nostrafe_waypoints.yaml`，重启 launch，无需编译。
