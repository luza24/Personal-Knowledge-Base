### R1 的关键修正

初版结论是「`turn: right` 写错」，用户指出**车确实在行进方向的右侧**。复核后确认：

- 航点 `car_2=(1.1,-1.1,yaw 0)`、`car_3=(1.1,-0.5,yaw 0)`（`sim_waypoints.yaml:39-48`）
- 车板在 `(1.65,-1.1)`、`(1.61,-0.5)`，即航点 **+x 方向 0.5 m**（`community.world:154-168`）
- 从 `car_1` 到 `car_2` 的行进方向是 **+y（yaw π/2）**，车在**右侧 +x**
- 但 `go_to()` 把航点 yaw=0 写进 move_base goal，TEB 的 `yaw_goal_tolerance: 0.12` 会强制车头转到 +x 才报成功
- 于是 `turn_in_place(right)` 得到 `0 + (-90°) = -90°`，相机背对车

所以**右转本身符合设计意图，错的是航点 yaw**：它应该是行进方向 π/2，而不是 0。其他站点的航点 yaw 基本都是「最后一段行进方向」，转向用来对准目标；`car_2`/`car_3` 是唯一不符合这条规律的两个点，更像是复制航点时漏改。

复算结果（已执行）：

```text
car_2 当前配置：wp.yaw 0 + right(-90°) = -90°  → 目标 0°，偏 90° → OUT
car_2 方案 A ：wp.yaw π/2 + right(-90°) = 0°   → 目标 0°，偏 0°  → IN
car_1 当前配置：wp.yaw 0，无 turn       = 0°   → 目标 0°        → IN
```

## 修改方案

### R1：改航点 yaw（推荐）或去掉 turn

方案 A（保留「沿车道走、车在右侧」的流程）：把 `sim_waypoints.yaml` 与 `real_waypoints.yaml` 里 `car_2`/`car_3` 的 `yaw` 改成 `1.570796`，`turn: right` 保留。

```yaml
  - name: "car_2"
    x: 1.1
    y: -1.1
    yaw: 1.570796      # 原来 0；朝向行进方向 +y，右转后正对 +x 的车
  - name: "car_3"
    x: 1.1
    y: -0.5
    yaw: 1.570796
```

方案 B：保持 `yaw: 0`，删掉 `turn: right`，让 move_base 直接把车头停在 +x。

无论哪种，**检测前的最终朝向必须等于车相对航点的方位角**（仿真里是 0°）。

### R2：OCR 不应阻塞图像回调

根因：`wait_for_ocr()` 在 `on_image` 里 `join(8.0)`；8 秒是 join 上限，不是 OCR 耗时。首次还要懒加载 `easyocr.Reader`（N100 上 5–20 s）。

修法三步：

1. 启动时后台预加载 easyocr；
2. 图像回调只把车牌裁剪图放进待处理槽，立即发布 `total/boxes + plate_done:false`；
3. 单线程 OCR worker 完成后校验 generation、补发 `plate_done:true` 的结果；mission 轮询到 `plate_done` 或超时再播报。

核心代码：

```python
# on_image：永不阻塞
if dets:
    best = max(dets, key=lambda d: d[1])
    self.submit_ocr(frame, best[2])
self.publish_result(dets)          # 立即发，plate 可能为空

# OCR worker
def _ocr_loop(self):
    while not rospy.is_shutdown():
        with self.job_lock:
            while self.pending_crop is None and not rospy.is_shutdown():
                self.job_cond.wait(0.5)
            crop, gen = self.pending_crop, self.pending_gen
            self.pending_crop = None
        text, conf = self.recognize(crop)
        with self.job_lock:
            if gen != self.ocr_gen:     # 上一站的任务，丢弃
                continue
            self.plate, self.plate_conf = text, conf
            self.plate_done = True
        self.publish_result(self.last_dets)
```

mission 侧把固定 `sleep(1.0)` 换成：

```python
payload = self.wait_for_result(
    target, 12.0 if target == "car" else 2.0,
    done_key="plate_done" if target == "car" else None)
```

### R3：导航超时改为有限值

`aic26_decision/launch/mission.launch`：

```xml
<param name="nav_timeout"        value="120.0"/>
<param name="nav_server_timeout" value="120.0"/>
```

`wait_ready()` 返回 False 时中止任务并报 ERROR；`go_to()` 失败重试一次后 `cancel_goal()`。

### R5–R13 摘要

- R5：`turn_in_place` 返回 False 时跳过本次检测或重试。
- R6：加 `~pass_on_no_data`（实车默认 false），返回 False 时记录失败。
- R7：OCR 任务带 generation；`on_detect` 不要无条件置 `plate_done=True`。
- R8：实车启动显式传 `initial_pose_y:=1.6`，或让默认值按 backend 取。
- R9：仿真 URDF 的相机/雷达位姿与 FOV 对齐实车图纸，或用实车图验证模型。
- R10：`get_num_connections()` 等待加 10 s 超时。
- R11：反馈超时后停止发布 `/vel_raw`，或在底盘节点发布 `feedback_age` 诊断。
- R12：`join` 前把 `self.ocr_thread` 取到局部变量。
- R13：识别成功后停止本站重跑 OCR（或限制尝试次数）。

## 结果与结论

- 审查完成，完整报告已写入 `C:\Users\luza\Desktop\aic1023_分析报告.md`；**尚未修改 aic1023 源码**。
- R1 的初版结论已被用户纠正，报告内的 R1 已同步改写为「航点 yaw 与转向逻辑不一致」。
- 已排除的伪问题：TEB `min_obstacle_dist=0.12`（是相对 footprint 边界的间距）、红绿灯视觉名不匹配（有三级回退）、`capture/demo` 用 subprocess 调 `day_night.py`（roslaunch 的 `__name` 不会冲突）、雷达 mask（launch/YAML 有意覆盖为全 360°）、局部代价图无 static layer（注释已说明）。
- 待验证：
  1. 实车车位布置是否同样是「沿车道、车在右侧」——决定 R1 选方案 A 还是 B；
  2. ONNX 输出布局是 YOLOv8（`4+nc`）还是 YOLOv5（多一列 objectness）；
  3. `angular_scale=0.96` 是否在命令侧和反馈侧被重复应用；
  4. N100 上 easyocr 冷启动的实际耗时。
- 下一步：按 R1/R2/R3 修改后，先在仿真跑一遍 `mode:=mission`，确认三个车位的播报。
