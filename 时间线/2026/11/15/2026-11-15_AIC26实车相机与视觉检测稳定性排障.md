# AIC26 实车相机与视觉检测稳定性排障

> 整理日期：2026年11月15日 12:38
> 项目：ROS仿真车 ｜ 类型：报错排查 ｜ 状态：部分解决 ｜ 主题：`感知与视觉`、`硬件与调试` ｜ 标签：`ros`、`真车`、`perception`、`yolo`、`openvino`

## 背景 / 目标

2026-11-14 在实车 `aic26_ws_112` 上排查一串相互关联的视觉问题：

- `bringup.launch backend:=real` 打不开相机；
- 视觉检测模型“没加载出来”，任务检测超时；
- 新增 HIK 红外相机后，V4L2 节点编号变化；
- 电动车（ebike）类别需要从 `fall` 改名为 `normal`；
- `ResultViewer` Tk 界面的目标按钮一行放不下，需要可滚动的目标选择。

目标是把相机、检测节点生命周期、GUI 和标签四条线一次梳理清楚，留下可复现的排查命令和修复。

## 报错记录

### 1. `/dev/video0` 不存在

`camera_node` 日志：

```text
camera: /dev/video0 full 1280x720 @ 30 fps ...
camera: idle -> view
camera: cannot open any of ['/dev/video0'] at 640x360
```

同时 `lsusb` 能看到 Orbbec 相机，但：

```text
lsusb -t:
  1-4.3:1.0  Driver=
  1-4.3:1.1  Driver=
```

`uvcvideo` 只绑定在 HIK 红外 `1-1` 上，Orbbec 的 UVC 接口被解绑，所以没有 `/dev/video0`。

原因在 `~/rc/station/server.py` 的注释里已经写明：

> The Orbbec SDK detaches uvcvideo from the RGB camera and never gives it back, so `/dev/video0` disappears after the driver stops.

触发方式是运行 `roslaunch orbbec_camera ...`（station 导航启动时也会自动拉起）。Orbbec SDK 退出后不会恢复 UVC 驱动。

### 2. 红外相机未枚举

HIK 红外最后一次正常工作在 20:53，之后内核日志出现：

```text
usb 1-1: USB disconnect
usb 1-1: device descriptor read/64, error -71
usb1-port1: Cannot enable. Maybe the USB cable is bad?
usb1-port1: unable to enumerate USB device
```

`lsusb` 完全看不到 `2bdf:0101`，`/sys/bus/usb/devices/1-1` 也不存在，station 的 `/api/ir.status` 返回：

```json
{"error": "没找到红外相机（没插好？）", "age": null}
```

这是电气/枚举层失败，不是 ROS 或 OpenCV 能修的；软件 USB reset 对该相机已验证无效，必须物理拔插或重启主机。

### 3. 检测模型“没加载出来”

检测器日志其实都显示加载成功：

```text
loaded person.onnx with openvino (CPU, 2 threads)
loaded ebike.onnx with openvino (CPU, 2 threads)
...
people_detector ready
fire_detector ready
```

但启动后约 5 秒，多个检测器收到：

```text
signal_shutdown [signal-15]
```

结果：

- `fire_detector`、`building_detector` 等 unregister，`/perception/detect` 只剩部分订阅者；
- mission 的 `detect start: fire` 全部 `no complete fire result within 5.0s`；
- camera 一直停在 640×360 view 模式，因为检测器没有订到 `/camera/image_raw`。

更严重的是系统里堆积了 **70 多个** `PPID=1` 的孤儿检测器进程，清理前：

```text
内存：已用 4.9Gi，可用 2.2Gi，swap 已用 1.7Gi
```

清理后：

```text
内存：已用 2.4Gi，可用 4.7Gi
```

孤儿来源：

```xml
launch-prefix="bash -c 'sleep $(arg node_delay); $0 $@'"
```

没有 `exec` 时，bash 把 Python 检测器当子进程启动；roslaunch 关闭时杀掉 bash 父进程，Python 检测器变成孤儿。并且 `cleanup_leftovers.py` 的 `PATTERNS` 原本不包含 `*_detector.py`，所以每次启动都不会清理它们。

`fire_detector` 收到 SIGTERM 后节点 unregister，但进程因 OpenVINO 原生线程没有退出，`respawn` 也不会触发，形成“活着但不在 ROS 里”的僵尸状态。

### 4. 楼宇/火焰的实际结果

`buildout_detector` 日志显示两次楼宇检测都完成了：

```text
layout_a: building request finished, counts=[2, 2]
layout_b: building request finished, counts=[1, 1]
```

真正失败的是 fire：它在启动时被 SIGTERM，之后两次 layout 的 fire 请求都超时。楼宇第二次若期望 2 个而实际 1 个，属于视角/遮挡/置信度问题，不是节点没启动。

### 5. ebike 标签语义

原模型类别：

```python
CLASSES = ['down', 'fall']
```

实际需要把第 1 类改成正常放置：

```python
CLASSES = ['down', 'normal']
```

对应 JSON 字段、播报文案和 GUI 都要同步，否则 mission 仍按“摔倒”播报。

## 修改方案

### A. 恢复 Orbbec UVC

使用免 root 的 usbfs ioctl，逻辑来自 station 的 `reattach_uvc()`：

```python
import fcntl, os, struct
for dev in Path('/sys/bus/usb/devices').glob('*'):
    if dev.joinpath('idVendor').read_text().strip() != '2bc5':
        continue
    if dev.joinpath('idProduct').read_text().strip() != '0561':
        continue
    node = '/dev/bus/usb/%03d/%03d' % (
        int(dev.joinpath('busnum').read_text()),
        int(dev.joinpath('devnum').read_text()))
    fd = os.open(node, os.O_RDWR)
    for ifno in (0, 1):
        fcntl.ioctl(fd, 0xC0105512,
                    bytearray(struct.pack('iiP', ifno, 0x5517, 0)))
    os.close(fd)
```

执行后 `/dev/video0`、`/dev/video1` 恢复，bringup 的 camera_node 自动打开：

```text
camera: opened /dev/video0 (640x360 @ 10.0 fps, MJPG, view mode)
camera: opened /dev/video0 (1280x720 @ 30.0 fps, MJPG, full mode)
```

`detect_gui.py` 已加入自动 reattach 和 Orbbec 优先选择：按 sysfs 名字找 `orbbec` 且 index=0，跳过 HIK 红外和 metadata 节点。

### B. 节点编号与相机选择

新增 HIK 后 V4L2 编号会变，实测两种状态：

```text
只插 Orbbec：video0=Orbbec(index0), video1=Orbbec(index1)
再插 HIK：  video0=HIK(index0), video2=HIK(index1)
            video1=Orbbec(index0), video3=Orbbec(index1)
```

不要硬编码 `/dev/video0` 给 Orbbec。稳定路径：

```text
/dev/v4l/by-id/usb-Sonix_Technology_Co.__Ltd._Orbbec_DaBai_DCW2_RGB_Camera_AUI7B4200J7-video-index0
/dev/v4l/by-path/pci-0000:00:14.0-usb-0:4.3:1.0-video-index0
```

`camera_node.py` 的 autodetect 目前按 `/dev/video*` 顺序尝试，HIK 在位时可能先选中红外；建议改为按 sysfs 名字优先 Orbbec、跳过 HIK，或在 bringup 命令行显式传 `camera_device:=<by-id 路径>`。

### C. 红外功能怎么用

两条路径：

1. station Web（`http://192.168.1.15:8780`）：右侧“相机 / 红外”切换；`/api/ir.mjpg` 看流，`/api/ir/shot` 保存 PNG + 同刻 RGB JPG 到 `dataset/ir/<日期>/`。
2. ROS：`roslaunch aic26_cobot ir.launch`，话题 `/camera/ir/image_raw`、`/camera/ir/image_raw/compressed`、`/camera/ir/active`，服务 `/camera/ir/snapshot`（默认存 `~/ir_snaps`）。

要点：

- 240×320 MJPG，10 fps；首次出图可等 30–45 s；
- 同一时间只能 station 或 ROS 节点占用；
- 使用 ROS 前先 `bash ~/rc/station/stop.sh`；
- 当前 HIK 需要物理拔插，`-71` 错误不能用软件 reset 修复；
- 代码目前只取伪彩热成像，没有像素温度反演；“D楼测温”只是任务标签。

### D. 检测器生命周期修复

1. `launch-prefix` 全部加 `exec`：

```xml
launch-prefix="bash -c 'sleep $(arg node_delay); exec $0 $@'"
```

2. 检测节点加自动重启：

```xml
<node ... respawn="true" respawn_delay="5.0">
```

3. 检测器 `main()` 在 `rospy.spin()` 后硬退出：

```python
rospy.spin()
# OpenVINO/native threads can keep the interpreter alive after SIGTERM.
os._exit(0)
```

4. `cleanup_leftovers.py`：

- `PATTERNS` 增加 `'_detector.py'`；
- 对 SIGTERM 不死的残留进程 1 秒后补 SIGKILL。

5. 清理当时 70+ 孤儿后，内存从 4.9Gi 降到 2.4Gi。

### E. ebike 标签改 normal

| 位置 | 修改 |
|---|---|
| `ebike_detector.py` | `CLASSES=['down','normal']`，JSON `normal`，debug 绿色 |
| `mission_common.py` | 播报“正常放置”；兼容旧 `fall` 字段 |
| `mission_controller.py` | summary 显示 `normal` |
| `detect_gui.py` | 目标类别和面板改为 `正常放置 normal` |

注意：`ebike.onnx` 文件内部 metadata 仍是 `fall`，本次只改运行时标签/JSON/播报。

### F. ResultViewer 目标滚动条

`ResultViewer._run_gui` 原来是一行 `Radiobutton`，目标多了会撑宽窗口。改为：

- `selector = tk.Frame(root)` 放在 `row=1, column=1`；
- 按钮放进固定宽度 `tk.Canvas`；
- canvas 下方加 `tk.Scrollbar(orient='horizontal')`；
- `buttons <Configure>` 时更新 `scrollregion`；
- 目标列表仍从 `IMAGE_TOPICS` 自动生成，未来新增目标自动出现。

实测布局：

```text
canvas_w=274  scrollregion='0 0 1080 25'
```

按钮行总宽 1080 px，显示区 274 px，滚动条生效。

## 结果与结论

- **Orbbec 相机**：UVC 重新绑定后恢复，bringup camera_node 能从 view 切到 full，检测能取到 1280×720 图；`detect_gui.py` 已能自动选 Orbbec。
- **红外**：当前 HIK 未枚举，需要物理拔插；station/ROS 用法已梳理，热成像没有温度数值。
- **检测器**：模型加载没有问题；问题是外部 SIGTERM + 孤儿/挂起。已加 `exec`、`respawn`、`os._exit(0)`、cleanup 清理；**SIGTERM 的发送者仍未确认**，日志中没有 roslaunch/cleanup 的杀进程记录，`rosrun` + `strace` 测试也没有复现，怀疑是启动后几秒内有外部 `pkill`/停止脚本/站点按钮操作。
- **楼宇/火焰**：楼宇两次请求实际都返回了结果（2 和 1）；fire 因启动被 SIGTERM 而未注册，属于检测器生命周期问题。
- **ebike**：`fall → normal` 已完成并测试播报。
- **GUI**：目标选择行已加水平滚动条，重启 bringup 后生效。

**待验证 / 遗留**：

1. 重启 bringup 后确认 8 个检测器全部注册，fire 不再掉线；
2. 确认 22:20 左右是否执行过全局 `pkill`/`rosnode kill`/站点停止；
3. station 与 bringup 同时抢 `/dev/video0`，测试 bringup 时先停 station；
4. 若需要长时间稳定，建议给 `camera_node` 加 Orbbec 优先/自动 reattach，避免 `/dev/video0` 编号变化和 UVC 解绑；
5. 楼宇 layout_b 计数 1（期望可能为 2）需看第二次调试图和视角。

## 2026-11-16 补充：双 bringup 栈同名检测器冲突

2026-11-16 21:56 的实车运行再次出现“部分任务点视觉模型没启动”。这次日志给出了明确根因：不是模型加载失败，也不是外部 `pkill`，而是**两套 `bringup.launch` 共用同一个 ROS master**。

现象与证据：

- 旧栈 `roslaunch` PID `171358` 于 20:36 启动后没有退出，并且它持有 `rosmaster`（PID `171372`）和 `rosout`（PID `171396`）；
- 新栈 `roslaunch` PID `221474` 于 21:56 启动，当前任务由它执行；
- 旧栈不停 respawn 9 个检测器，和新栈同名；
- 21:59:36 日志：

```text
external shutdown request from [/master]: [/people_detector]
Reason: new node registered with same name
```

- 21:59:38 任务报：

```text
no complete people result for 0a2ad78d:14 within 4.0s
```

- 22:00:39、22:01:02 又分别出现 `no complete rubbish result`、`no complete building result`；
- 两套栈的检测器日志都显示模型加载成功（`loaded person.onnx ... ready`），所以不是模型问题。

处理过程：

1. 先冻结旧 `roslaunch`（`SIGSTOP`），只杀旧检测器子进程，保留 master/rosout 和当前任务；
2. 新栈检测器恢复为每个节点一个实例，PID 与 `rosnode info` 一致；
3. 当前任务在 22:01:40 正常结束；
4. 随后彻底清理两套栈：停新栈，杀旧 `roslaunch`、`rosmaster`、`rosout` 及全部残留节点；
5. 验证 `11311` 端口释放、无 aic26 进程、僵尸进程为 0。

结论：

- 一个 ROS master 只允许一套 `bringup.launch`；
- 只杀检测器不够，旧 `roslaunch` 会继续 respawn，必须先停/冻结父 `roslaunch`；
- 启动前至少检查：

```bash
pgrep -af 'roslaunch aic26_bringup'
ss -ltnp | grep 11311
rosnode list
```

之前 11-14 的检测器 `SIGTERM` 是否也来自同名顶替尚未确认，但本次至少证明同名注册会产生 master 发起的 `external shutdown`。该问题属于运行态冲突，代码本身没有修复；需要在启动流程或操作规范上保证单栈运行。
