## 现状与关键结论

### 1. 运动控制没有 PID

控制链：

```
rotate_to() --/cmd_vel--> chassis_node --10 Hz 串口帧--> STM32
                                      <--20 Hz 速度反馈--
                         积分 odom + 融合 WIT 陀螺 z 角速度
                                      --30 Hz--> /odom、/vel_raw、TF
                          AMCL --map->base_footprint TF-->
```

- 底盘层 `chassis_node.py` 是**开环直通**：只做缩放、限幅、死区、10 Hz 下发，反馈只用于 odom 和告警，不修正下发速度
- 导航层是 `move_base` + `teb_local_planner`（TEB 是轨迹优化，不是 PID）
- 唯一的闭环在 `aic26_decision/scripts/mission_common.py:351` 的 `rotate_to()`，是**纯 P**：

```python
error = wrap_angle(target - yaw)
if abs(error) < self.turn_tolerance:
    self.stop_motion()
    rospy.sleep(self.turn_settle)
    return True

direction_sign = 1.0 if error >= 0.0 else -1.0   # ±π 附近保留原方向
cmd.angular.z = direction_sign * min(
    self.turn_speed,
    max(self.turn_min_speed, 3.0 * abs(error)))
self.cmd_pub.publish(cmd)
rate.sleep()
```

- 参数：`turn_speed=0.8`、`turn_min_speed=0.15`、`turn_tolerance` 代码默认 0.05、**四个 launch 都覆盖为 0.10**、`turn_rate=20 Hz`、`turn_timeout=20 s`、`turn_settle=0.5 s`
- 全仓库没有 PID 类、积分项、微分项、抗饱和代码

**为什么 PID 收益可能有限**：

- 容差 0.10 rad ≈ 5.7°，误差 0.10 时 P 输出 0.30 rad/s，20 Hz 每步 0.015 rad
- 最大 0.8 rad/s 时每步 0.04 rad，仍小于容差，单步不会跳过窗口
- 最小速度 0.15 只在 `|error| < 0.05` 时生效，而 0.05 已在 0.10 停车窗口内，正常走不到
- 主要误差源是**延迟**（10 Hz 下发 + 20 Hz 反馈，约 100–200 ms，对应 4.6–9.2°），不是缺 I/D
- D 项作用于 `map` TF 时会被 AMCL 跳变放大；必须测量值微分 + 低通，或改用 odom/IMU 角速度
- I 项在 5.7° 容差下很可能不必要，反而在到位附近积分饱和造成超调

因此对 PID 的定位应是：**控制器工程化 + 可观测性 + 安全兜底**，PID 是待数据验证的假设，不是目的。

### 3. 加更多目标点位不会自动提升导航稳定性

当前实现里，航点不是路径采样点，而是**独立的 move_base 目标**：

- `waypoint_follower.py` 逐点调用 `go_to()`，等每个 goal `SUCCEEDED` 才发下一个
- TEB `free_goal_vel: false` → **每个点都减速到零**
- 到点需满足 `xy_goal_tolerance=0.10 m`、`yaw_goal_tolerance=0.12 rad`
- 每个点都是一次新的全局规划、TEB 初始化与终点朝向收敛

所以加点的直接后果：

1. 停车次数变多，走—停—走，时间变长
2. 终点朝向修正次数变多，点附近更容易来回扭
3. 失败面变大：每个点都可能 `NO PATH!`、`not feasible`、`oscillation`、恢复行为
4. 贴墙风险叠加

现有 14 点路线的证据（来自 2026-10-26 导航验收）：

- 已有 5 个“贴边”点：`traffic_light_1`、`station_1`、`station_3`、`corner_4`、`corner_5`
- `corner_5 (-0.05, 0.65, 270°)` 贴墙，TEB 为满足终点朝向绕行/掉头：实际 6.05 m（直线 2.60 m），耗时 57 s
- 一次完整路线出现 `NO PATH!` 19 次、规划失败 24 次、TEB `not feasible` 20 次、Recovery 2 次
- AMCL yaw 真实分辨力约 ±1–3°，还有约 6° 的绝对偏差；到点 yaw 容差 6.87°，余量不足 1°
- 前 12 点均 `SUCCEEDED`、0 ABORT，说明底盘/陀螺/定位跟踪本身正常，问题集中在目标点几何与终点朝向

**加点唯一有用的场景**：稀疏的路径引导点，放在拐角、窄道入口/出口，防止全局规划抄近道或走错走廊。有效前提：

- 离墙至少 0.15 m 余量
- yaw 与下一段行进方向一致，不逼 TEB 原地掉头
- `dwell: 0`，且不写进 `real_tasks.yaml`，避免多触发检测/播报
- 每个拐角 1–2 个，整条路线加 3–5 个，而不是几十个

**加点解决不了**：长直线蛇形、定位跳变、到点朝向差、贴墙导致的无路可走。这些要靠地图/初始位姿/AMCL、目标点外移、`rotate_to` 二次对准。

## 结果与结论

- **PID 检查**：没有 PID；`rotate_to` 是纯 P（增益 3.0 + 最小速度），底盘开环，导航用 TEB
- **PID 必要性**：在 0.10 rad 容差下，最小速度和 I 项基本不参与；主要误差源是延迟与 AMCL 朝向不确定，PID 本身收益需数据验证
- **加点结论**：不会自动提升稳定性；当前实现下通常更慢、失败面更大；只有稀疏拐角/窄道引导点有价值
